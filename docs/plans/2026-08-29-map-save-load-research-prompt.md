### 1. 我们到底想从这次调研拿到什么

委托方**已经冻结了一套存档的公共契约**（第 3 节的画像：规范字节、快照 / 差分 / 持久化确认 / 驱逐栅栏 / WAL 哈希链都已定义），但**契约之上的整条工程链路几乎是空白**：怎么冷启动读、懒加载由谁触发、内存怎么控、Minecraft 地图怎么导进来、格式改版后旧存档怎么办、地图内容更新怎么发给玩家——这些都还没有答案。

具体想拿到五样东西：

1. **一条完整的存档链路，端到端** —— 从「磁盘 / 网络上的一堆字节」到「玩家眼前可交互的世界」，中间每一步是什么、发生在哪个线程 / 哪一帧 / 哪一相。同样地，从「玩家挖了一个方块」到「这个改动在断电后还在」，中间每一步是什么。**要能画成两张时序图。**
2. **每一个设计背后的那个坑** —— 不要格式字段罗列。为什么 Minecraft 的区域文件要按 4KiB 扇区分配？为什么 1.13 之后方块要改成 palette + 位打包？为什么区块超过 1MiB 要外置成单独文件？为什么会有 `DataVersion` 这个字段、以及为什么 Mojang 要专门写一个数据修复库？**每个设计背后都有一个具体的、可复述的事故，把那个事故挖出来**——这比记住字段名有价值一百倍。
3. **三个最高优先级重点（本次调研的核心）：**
   - **Minecraft 地图数据的完整解剖**：Java 版与基岩版的存档结构、区块编码、ID 与调色板、版本演进机制。要精确到「照着能写出解析器」。
   - **读档性能与懒加载 / 内存策略**：冷启动、随机寻址、解压、并行、驻留上限、驱逐、抖动——客户端与服务器两条完全不同的画像。
   - **存档格式的版本管理与地图内容的更新分发**：格式改了、方块定义改了、地图本身改了，玩家手上的旧存档怎么办。
4. **可执行的导入管线设计输入** —— 委托方计划做一个「把 Minecraft 地图导出到本项目」的转换工具。这次调研要给出：这类工具**必须做出的决策清单**、**必然踩的坑清单**、以及**已有工具是怎么做的**。
5. **完整性缺口清单** —— 这是本次调研**最核心的交付物**。对照第 3 节的画像，逐条指出「同类存档系统普遍具备、而这张画像里压根没提到」的能力与语义。宁可多列，也不要漏。

最终这份报告要能回答一个问题：**这套已冻结的存档契约，离一个能扛住大世界、双端读取、内存受限、可持续更新的生产级存档系统，还差哪些东西；这些差距里哪些是必须现在补的，哪些可以推迟。**

### 2. 硬性规则（违反即退回重做）

1. **证据先于声称。** 每条技术论断必须可追溯到：① 官方文档 / 格式规范（给 URL 或页面标题）；② 开源仓库路径 + 类 / 函数 / 字段名（给仓库全名，如 `owner/repo`）；③ 论文（标题 + 作者 + 年份 + 出处）；④ 明确标注的社区来源（作者 / 平台 / 文章标题）。

### 3. 目标环境画像（用于判断可迁移性；自包含，不需要查任何代码）

这是委托方引擎的当前形态。做对比与缺口分析时以这张画像为准。**画像里已冻结的部分不要评审对错**，你的产出是「工业界怎么做 + 这个做法能不能在这套约束下成立 + 代价是什么 + 缺了什么」。

| 维度 | 目标环境的形态 |
|---|---|
| 项目形态 | 自研游戏引擎的体素世界。服务器权威模拟，客户端跑只读副本世界。近期目标：多个**浏览器**客户端登录同一个体素世界联机，挖 / 放方块实时互见。 |
| 语言与运行时 | **权威体素世界是 Rust 原生实现，跑在服务器**；**客户端在浏览器里跑 .NET WASM**，副本世界由一套**纯 C# 的参考实现**承载。**两套独立实现必须语义等价**——同一串 Mutation 序列必须产出一致的快照哈希（差分测试是硬验收项）。 |
| 世界与角色 | 世界实例分 `Authority` / `Replica` 两个角色，**各自独立的存储与实体命名空间**；单机形态下两个角色是同进程内的两个独立实例，不共享存储。 |
| 分块模型 | 三维 Chunk 分块。Chunk 坐标每轴 **signed 32-bit，负坐标一等公民**；规范 ChunkId 字符串是 `c:<x>:<y>:<z>`（**无前导零、无 `-0`**），并且是所有 chunk 键控映射的强制键格式。方块值过线为 **unsigned 32-bit**。 |
| 分页 | Chunk 内部再分 page。每页带 `pageIndex`、`pageVersion`、`encoding`（`Dense` / `Sparse`）、`payloadLength`、**SHA-256 哈希**、`compression`（`None` / `Zstd` / `Lz4`）。页哈希不匹配一律拒绝，**绝不静默零填充**。 |
| Chunk 状态机 | `Unallocated, Loading, Ready, Dirty, Evicting, Unloaded, Failed`。 |
| 铁律一 | **缺失的 chunk 永远不等于空世界。** 未加载 / 加载中 / 不可用必须经显式的 presence 枚举上报（`Ready` / `NotLoaded` / `Pending` / `Unavailable`），不得当作空气方块返回。 |
| 修订号 | `WorldRevision` 每世界单调递增，`ChunkRevision` 每 chunk 单调递增；每个读结果都带一个 revision stamp（`{worldId, context, worldRevision, chunkRevisionSet}`）。 |
| 读一致性 | 两种模式：`ExplicitRevision` 或 `LatestAtBegin`。**目标修订在请求开始时绑定**，整个读集合共用同一个 `boundWorldRevision`；分页续读携带同一个绑定值、**永不重绑**；绑定的修订若已被回收，请求以 `TargetRevisionUnavailable` 终止，**绝不静默降级读最新**。 |
| 快照信封 | 通用 `snapshot-header` 信封（魔数、schema 版本、激活状态、加密元数据、时间戳、payload 哈希）+ 体素域 payload。信封与 payload 的修订字段必须相等，不等即校验失败。 |
| 快照的规范字节 | **同一个 cut，在任何合规编码器上、任何时候，产出逐字节相同的 payload。** 因此 manifest 里**没有墙钟时间戳、没有可选字段**；chunk 表是**数组不是 map**；唯一规范序是 `CoordXYZAscending`（x 升序、再 y、再 z）；每条目的 `byteOffset`/`byteLength` 连续升序且求和等于总长；`payloadHash` 是规范字节的 SHA-256。**同 cut 两次编码字节不同 = 致命契约违规，不是可容忍的抖动。** |
| 快照三种形态 | `Full`（全量）/ `Partial`（显式的 AOI 子集，**payload 里缺席的 chunk 是「未覆盖」，不是「已删除」，恢复时绝不materialize 成空块**）/ `Diff`（引用 `baseSnapshotId` + `baseWorldRevision`，目标以**严格为正**的 `worldRevisionAdvance` 表达；base 不匹配则失败并保持原状，**唯一降级路径是重新做全量，禁止静默 rebase**）。 |
| 捕获生命周期 | `Requested -> Cutting -> Pinned -> Encoding -> Verified -> Ready -> Released`，异常退出到 `Cancelled` / `Failed`。**只在一个短 barrier 内**建立 Pin 或写时复制视图，随后立刻恢复正常权威写入，编码异步跑在这个不可变视图上。**为整个编码时长停写不是合规实现。** `Verified`/`Ready` 要求 pin 仍然持有；pin 预算耗尽 / 目标修订被回收只能走 `Failed`。 |
| 写侧持久化确认 | 宿主的持久化编排通过一条 `DurabilityAck` 记录向世界确认落盘：覆盖的 chunk 集合（`{chunkId, upToChunkRevision}` 数组，规范序）、`coveredWorldRevision`、以及一个 `durabilityPoint`（快照引用 / WAL 位置 / 两者兼有，**三选一，结构上判别**）。**只在 barrier 应用，幂等**；chunk 的脏标记只对 `<= upToChunkRevision` 的修订清除，之后的写入仍然脏。 |
| 驻留与驱逐 | 世界创建时声明**唯一且不可变**的驻留策略：`AllResident`（禁止卸载）/ `DurableEviction`（默认：只有被确认覆盖才能卸载）/ `VolatileAllowed`（显式声明的丢失边界，需要专门的能力位）。**脏 chunk 没有确认覆盖就不许离开驻留**，否则报错并保持驻留；每次驱逐决策都产出一条可审计的栅栏记录，脏 chunk 的 `Evict` 必须恰好命名一条保护路径。专用服务器默认不允许 `VolatileAllowed`。 |
| WAL | 恢复记录带 `recordSeq`、`idempotencyKey`、`previousHash`、`payloadHash`、`length`、`commitState`、`durabilityState`、`checksum`，**前后哈希链**。日志 / 观测事件**不得**充当恢复输入。 |
| 帧模型 | 逻辑 Tick 分相推进，**一帧内唯一的结构提交点**；提交点之前的写入对复制与快照不可见。 |
| 故障模型 | Tick 内故障 **fail-stop**：不做字段级撤销，**整帧作废**，从快照 + 日志重建。 |
| 写盘纪律 | 快照写入走 staging、校验、fsync / 原子激活，并保留上一个有效检查点。损坏 / 不兼容 / 超预算的数据**永远不会被激活**，且不破坏上一份快照。恢复从最后一个有效检查点开始，只重放**已认证且已提交**的日志记录。 |
| 迁移 | 从**不可变的**快照 id + 会话修订向量读入，按声明式**有向无环图**在 staging 目录执行转换，校验 schema / 引用 / 资源配额 / 目标清单，成功后**原子切换版本指针**。失败不得覆盖旧数据，保留旧快照与可重跑证据。**同一 Release 下单机与专用服务器的存档可互转；跨版本必须有显式的 Migrator。** |
| 发布 | 发布目录按「产品 id + 发布 id」路由；一个进程只装一个 Release；当前版本要求**服务端与客户端 Release 精确匹配**。滚动更新与强制维护有独立状态机（本次调研**不展开**，见第 1.1 节边界）。 |
| 资源预算 | 世界创建时从不可变配置拿到硬预算：最大驻留 chunk 数、快照 pin 字节预算、最大并发查询数、最大待处理 mutation 数、回执保留条数。**超预算返回明确错误，不静默成功、不静默截断。** |
| **尚未冻结** | **chunk 尺寸、世界高度 / 边界、page 大小、方块存储与压缩后端、查询与预算默认值**——目前只有适配器内部的实现族（各向同性立方体范围、稠密未压缩、压缩标识 `None`），**消费方不得依赖具体数字**。**捕获物化策略（Pin 还是写时复制）、子 chunk 级 diff 粒度、驱逐候选打分与滞后**也全部未定。**本次调研的结论会直接影响这几项选型。** |

#### 已知待解的硬问题（调研时请特别留意同类系统的答案）

1. **冷启动读档路径**：一个全新进程从 0 到「世界可交互」，先读什么、读多少、在哪一相读、读的过程中 Tick 跑不跑、玩家在读的过程中能不能进来。
2. **懒加载的触发源到底是谁**：AOI？玩家位置？显式查询？预测？加载天然是异步的，但一帧只有唯一提交点——**异步加载完成的 chunk 如何落到提交点上而不撕裂修订号**。
3. **`Partial` 快照（AOI 子集）能不能直接当客户端存档用**；浏览器客户端要不要存档、存哪里（浏览器持久化设施的容量、配额、驱逐行为）。
4. **「同 cut 逐字节相同」与压缩后端的冲突**：Zstd / Lz4 的不同实现、不同级别、不同版本会不会产出不同字节？**两套独立实现（Rust 与 C#）怎么同时满足这条铁律？** 工业界有没有先例，代价是什么。
5. **Diff 只到 chunk 粒度**时，一个 chunk 改一个方块要重传整块——什么时候必须下沉到 page / 子 chunk 粒度，下沉的代价是什么。
6. **「脏 chunk 不许无确认卸载」与浏览器内存受限直接冲突**：副本世界的「脏」是什么意思？客户端能不能丢？丢了怎么补？
7. **Minecraft 的方块 ID / 数据版本 / 高度范围 / 分节结构如何映射到本项目的 chunk / page 模型**；映射表本身怎么存、怎么版本化。
8. **存档格式的版本演进**：加字段、改编码、**改 chunk 尺寸**、换压缩后端时，旧存档怎么办；哪些必须离线迁移、哪些可以就地兼容读。
9. **地图内容更新与玩家已有修改的合并**：我们改了地图或方块定义，玩家已经挖过那片地——这是覆盖层与内容更新的经典冲突，工业界怎么解。
10. **客户端与服务器读的是不是同一份存档格式**，还是客户端读的是一份「投影格式」。

#### F. 内存驻留、懒加载与卸载（**最高优先级重章之四**）

- **驻留集怎么定**：固定上限、按内存水位、按视距、按玩家数。**多个玩家分散在世界各处时驻留集会爆炸——工业界怎么控。**
- **加载的触发源**：视距 / AOI、玩家位置、显式查询、物理与光照的邻块需求、实体活动、以及「已加载块的边界需要邻块」这类**级联加载**。把触发源列全，并指出**哪些是隐蔽的、容易把驻留集撑爆的**。
- **卸载策略**：LRU、按距离、按访问频率、分代、以及滞后带 / 双阈值抖动抑制。**玩家在边界来回走导致的反复加载卸载**，各家怎么防、有没有公开参数经验值。
- **脏块不能随便丢**：committed 但未持久化的修改怎么办——先落盘再卸载？还是禁止卸载？工业界的做法与失败案例。**委托方在这里有硬约束（脏块未被确认覆盖不许卸载），重点找同类先例与它们的代价。**
- **分级驻留 / LOD**：完整块、压缩驻留块、仅元数据、仅高度图、完全卸载——**多级驻留是不是主流？** 每级的内存占用与降级 / 升级成本。
- **摊销**：一帧最多加载 / 卸载多少块、加载预算怎么表达、超预算怎么排队、饥饿怎么防。
- **内存表示的省法**：调色板 + 位打包常驻内存（不只是磁盘上）、稀疏结构（八叉树 / 稀疏体素结构 / 分块哈希）、驻留时压缩、值类型与免分配路径。**托管运行时（C#）下的 GC 压力与大对象堆问题单独说。**
- **浏览器 / WASM 侧的特殊约束（重点）**：线性内存的上限与「只增不减」的行为、增长时的拷贝停顿、GC 行为、浏览器持久化设施（各种客户端存储）的**容量、配额、被系统回收的可能性、同步 / 异步 API 差异**。**在浏览器上做一个内存受限的体素副本世界，工业界有没有先例？找出来。**
- **实测量级**：多少 chunk 常驻占多少内存？谁公开过数字与配置。**引用出处；没有就标 `Estimated`。**

#### G. 写档路径：脏块、增量、WAL、快照与持久化确认

- **一次方块修改到落盘的完整链路**：内存改 → 标脏 → 提交点 → 日志 → 快照 / 增量 → fsync → 确认 → 清脏。工业界的几种链路形态，逐个对比。
- **周期性快照 vs 写时落盘 vs 日志为主**：三种策略的取舍（数据丢失窗口、卡顿、写放大、恢复时间）。**谁在用哪种。**
- **快照期间不停写**怎么做：写时复制、双缓冲、pin + 版本链、LSM 式不可变段。每种的内存放大与实现复杂度。**委托方的契约要求「短 barrier 建视图 + 异步编码」，重点找同构先例。**
- **增量 / diff 的粒度**：整块、页、子块、单方块事件流。粒度对存档体积、恢复时间、编码 CPU 的影响。**什么时候必须做 base + 一串 diff 的链，链多长要重做全量。**
- **自动保存的卡顿**：大世界自动保存导致的帧率尖峰是老问题——工业界的缓解手段全清单（分帧摊销、后台线程、增量、限流），以及各自的副作用。
- **持久化确认回传**：谁告诉世界「这些块已经安全了」？有没有同类系统做到修订号级精确覆盖？没有的话它们用什么（布尔标记？时间戳？序列号？），代价是什么。
- **玩家数据与世界数据的落盘时序**（薄，只画边界）：两者是同一个事务吗？不一致会出什么问题（复制物品是经典事故）——**举具体案例，然后交给第 O 章。**

#### H. 崩溃一致性、损坏与修复

- **崩溃点全清单**：写到一半断电、fsync 前断电、目录项未落盘、区域文件头写了但数据没写、快照激活到一半——每种会留下什么现场，怎么检测。
- **原子激活**：临时文件 + 重命名、双缓冲指针、版本目录 + 符号链接、日志 + 检查点。各自在不同文件系统 / 平台上的实际保证（**注意：某些保证在部分平台上并不成立，找出来**）。
- **恢复流程**：从哪个检查点开始、重放多少日志、幂等怎么保证、重放到一半再崩怎么办。
- **损坏检测与修复工具**：工业界的存档修复工具都做什么（重建索引、丢弃坏块、从备份补、重新生成）。**Minecraft 生态在这块工具很多，重点挖它们的做法与用户反馈的实际效果。**
- **备份与保留策略**：保留几份、什么时候滚、增量备份、以及「玩家自己手动备份」这个现实。
- **真实事故案例**：找公开记述的存档损坏 / 丢失事故，**每个都写清根因与后来的修复措施**。这一节的价值全在具体案例上。

#### I. 双端读档：客户端与服务器的两条不同画像

- **服务器读档画像**：全世界 or 活跃区域、多玩家分散、长时间运行、内存相对充裕、要求权威与可恢复。
- **客户端读档画像**：只关心自己周围、内存紧、要求首帧快、可以丢弃可重建的数据、**而且可能根本没有本地存档（全靠网络流式接收）**。
- **客户端到底要不要有本地存档**？把三种形态列全并对比：
  - 纯流式（网络给什么算什么，本地零持久化）
  - 本地缓存（缓存服务器发来的块，用哈希 / 修订号校验是否过期）
  - 完整本地存档（单机 / 离线形态）
- **本地缓存的失效与校验**：拿什么当缓存键（chunk 修订号？内容哈希？世界版本？），过期怎么判，服务器怎么告诉客户端「你缓存的那块已经变了」。**这一节直接对应委托方的浏览器客户端，写厚一点。**
- **同一份格式还是两份格式**：客户端读的是不是服务器那份存档格式？工业界的选择与理由。**「一份格式两套实现」的语义漂移风险**（委托方有 Rust + C# 两套实现且要求哈希一致，重点找先例与它们怎么防漂移：差分测试、共享测试向量、规范字节）。
- **网络传输的块格式与磁盘的块格式是不是同一个**：合一的收益（省一次转码）与代价（磁盘格式被网络需求绑架）。谁合一了、谁分开了。
- **单机与联机存档互转**：同一份存档在单机与专服之间搬动，工业界怎么做、有什么坑（**委托方明确要求同 Release 下可互转**）。

#### J. 世界生成与存档的分工：存什么、不存什么

- **「只存改动」这条路线**：地形由种子 + 生成器确定性重算，存档只存玩家改过的部分。**谁在用？收益多大？**
- 这条路线的**致命依赖**：生成器必须永远确定性、且**永远不能改**——因为改了生成器，老存档没存的部分就变了。工业界怎么处理这个约束（版本化生成器？生成器版本进存档？改了就全量落盘？）。**找具体的事故案例：某个版本改了地形生成，旧世界边界出现地形断层——这类案例很多，挖出来写透。**
- **混合方案**：生成一次就落盘 vs 永远重算 vs 只对「被访问过」的区块落盘。三者的磁盘 / CPU 取舍。
- **生成阶段与依赖**：地形 → 装饰 → 结构 → 光照，每一步都依赖邻块，导致**级联生成**。存档里怎么记录一个块生成到了哪一步、怎么防止级联爆炸。
- **对委托方的直接意义**：画像里**世界生成完全空白**，而 Minecraft 导入进来的地图是「已经生成好的」。**「导入的地图」与「程序化生成的地图」能不能共存在同一套存档模型里？边界在哪？**——这一问必须给出明确判断。

#### K. 方块 ID、注册表与命名空间的存档表达

- **数值 ID vs 字符串 ID**：存档里存哪个？两者各自的问题（数值 ID 冲突与不稳定、字符串 ID 的体积与查表成本）。
- **每存档的 ID 映射表**：把「字符串 ID → 本存档内数值」的映射随存档一起存，是不是主流做法？谁在用？**这套机制怎么处理「新版本新增方块」「方块被删除」「方块改名」。**
- **模组 / 内容包带来的 ID 问题**：装了内容包又卸载，存档里那些块怎么办（占位？丢弃？拒绝加载？）。工业界的处理与用户体验后果。
- **方块状态 / 属性的表达**：变体、朝向、连接状态是编进 ID 还是单独字段？各自对存档体积和查询效率的影响。
- **对委托方的直接意义**：画像里方块值是 unsigned 32-bit，**但「这个 32 位的数字是什么含义」完全没定义**。给出可选方案与取舍，以及**这个决定与 Minecraft 导入映射表的耦合关系**。

#### L. 存档格式的版本管理与迁移（**重章**）

- **版本标识**：存档里记的是格式版本、引擎版本、内容版本，还是全都记？谁记在哪一层（文件头？每块？每字段？）。**多层版本号的经典混乱与解法。**
- **兼容策略全谱**：只能同版本读 / 向后兼容读旧 / 双向兼容 / 读时就地升级 / 离线批量迁移 / 拒绝并要求用户显式迁移。**逐个给出适用条件与代价。**
- **读时就地升级（重点）**：加载一个旧块时顺手升级到当前格式——这是 Minecraft 式做法。它的工程形态是什么（一串按版本编号的修复规则，逐级链式应用）？规则怎么组织才不会互相打架？**规则集会不会无限膨胀，怎么退役老规则。**
- **离线批量迁移**：staging + 校验 + 原子激活的成熟形态；大世界迁移要多久；能不能断点续跑；失败怎么回滚。
- **破坏性变更的处理**：改 chunk 尺寸、改高度范围、换压缩后端、换坐标语义——**这几种是「不能就地升级」的典型，工业界怎么做**（重新生成？强制全量迁移？拒绝？）。
- **降级**：新版本存档能不能被旧版本打开？行业普遍态度是什么、为什么。
- **版本演进的可测性**：怎么保证「所有历史版本的存档都还能被当前版本正确读出来」？**测试语料库（把历代版本的存档样本存起来当回归测试）是不是标准做法？谁在做？**
- **对委托方的直接意义**：画像里迁移只到「DAG + staging + 原子激活」的骨架，**没有任何「读时升级」机制，也没有历史存档语料库**。给出建议。

#### M. 地图内容的更新与分发（**重章**）

**边界提醒**：这一章讲**「新内容怎么和玩家的旧存档共存」**，不讲部署 / 运维（那在第 N 章，且不展开）。

- **核心冲突**：我们更新了地图（改了地形、加了建筑、改了方块定义），而玩家已经在那片地上挖过了。**工业界怎么合并？** 把做法列全：
  - 覆盖层模型（原始地图只读 + 玩家改动作为差分层叠加）
  - 分区更新（只更新玩家没碰过的区块）
  - 强制重置（明确告知玩家某区域会重置）
  - 版本分叉（旧存档留在旧地图上）
- **覆盖层模型深挖**（这条对委托方最相关）：底图与改动层怎么分离存储、读的时候怎么合并、改动层怎么压缩、底图更新时改动层怎么重定位、**改动层里「把方块挖成空气」和「底图本来就是空气」怎么区分**（这是覆盖层的经典坑）。
- **内容包 / 资源包 / 数据包的版本机制**：内容与存档的版本约束怎么表达、不匹配怎么办、有没有「格式版本号 + 兼容区间」的成熟设计。
- **增量分发**：只把变化的部分发给玩家。已有做法：二进制差分、按块哈希比对、内容寻址分块、清单 + 按需拉取。**每种给出适用场景与代价。**
- **按需 / 流式分发（重点，且对浏览器客户端极相关）**：把地图放在静态托管上，客户端用 HTTP Range 按需拉取自己需要的块——**这在其它领域（地理信息、科学数据、三维场景流式加载）是成熟做法**。把这些领域的做法搬过来讲清楚：容器格式怎么设计才能被范围读、索引放哪、缓存与 CDN 怎么配合、**这套做法对存档格式提出了什么额外要求**。这一节可能是本次调研最有迁移价值的部分之一，**认真挖。**
- **完整性与信任**：分发的地图数据怎么校验、怎么防篡改、客户端信任边界在哪。
- **回滚**：内容更新出了问题要回退，玩家在新版本里产生的改动怎么办。

#### R. 批评、失败案例与边界

- **区域文件式布局的公认痛点**：碎片、空洞、扇区浪费、超大块、并发写、修复困难。
- **嵌入式 KV 式布局的公认痛点**：compaction 停顿、写放大、空间放大、单进程独占、崩溃后的修复时间。
- **「只存改动 + 重算地形」的公认痛点**：生成器不可变、跨版本地形断层、重算 CPU 开销。
- **覆盖层模型的公认痛点**：空气与未改动的歧义、底图更新后的重定位、改动层无限增长。
- **懒加载的公认痛点**：抖动、级联加载、边界穿帮、加载卡顿、实体在未加载区域的行为。
- **什么规模 / 什么品类下这套思路会崩**：给出可操作的判据（世界体积？玩家数？改动密度？块尺寸？）。
- **放弃过某条路线的项目**：为什么放弃、换成了什么。**有公开记述就引用；找不到就明说找不到，不要编。**

- **压缩包里不要放**：下载来的源码或仓库内容、二进制、截图、临时文件。**总大小控制在 20 MB 以内。**
- 保留字母章节编号便于交叉引用；**每章末尾一个「来源」小节**，用编号回指 `sources.md`。

- **两张时序图是硬指标**：① 从「磁盘 / 网络上的一堆字节」到「玩家眼前可交互的世界」；② 从「玩家挖了一个方块」到「这个改动在断电后还在」。图源建议同时放进 `appendix/`。

**报告开头必须有**：

- **信息源可达性声明**（能否联网、能否打开各目标仓库并搜索、能否读到格式规范全文、能否访问中文社区）

- **被剖析对象的版本清单**（尤其 Minecraft：本次结论覆盖哪些版本区间）
- **执行摘要**：一页之内讲清最重要的十个发现
- **已知缺口清单**：哪些问题没查到、卡在哪里

**写作要求**：

- 每章开头三行「结论先行」摘要，再展开。
- 中文正文，技术专名保留英文原名，不要生造译名。
- 结论与推测分开：推测一律写「推测：」并说明推断依据。
- **篇幅不设上限**，信息密度优先于简洁。宁可长，不要空。但不要为了凑长度重复同一个论点。
- B / C / E / F 四章是重点，不许一笔带过；技术专名与格式字段名保留英文原名。

### 7. 交回物格式

交付时在会话里按五段回复（**附件 + 正文，缺一不可**）：

1. **产出**：上传的 zip 文件名与大小、包内文件清单、报告规模（章节数、字数量级）。
2. **执行摘要全文**：直接贴在正文里，**不要让委托方为了看结论去解压。**
3. **调研证据**：实际用到的信息源清单（分类计数）+ **信息源可达性的实际情况**——哪些打开了、哪些打不开、哪些块是源码级证据、哪些只是文档级。**不要只写「已完成」。**
