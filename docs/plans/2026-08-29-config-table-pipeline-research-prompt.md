### 1. 我们到底想从这次调研拿到什么

委托方**已经冻结了配表的契约面**（第 3 节画像的「已冻结」部分：列类型系统、校验规则、Staged/Active 双快照、Tick Barrier 原子激活、签名激活），但**完全没有冻结实现面**：用什么权威源、编译成什么格式、怎么加载、怎么懒加载、怎么压缩、怎么分端、怎么让 AI 参与配表——全是空的。本次调研就是把这块空白填上。

具体想拿到六样东西：

1. **一张能直接拿来做决策的格式选型矩阵** —— 候选的中间格式与运行时格式（JSON / MessagePack / Protobuf / FlatBuffers / Cap'n Proto / rkyv / Arrow-Parquet / SQLite / 自研 typed binary / …）在**零拷贝、随机访问、列裁剪、schema 演进、跨语言、WASM 可用性、常驻内存、可 canonical 化算 hash、压缩配合度、可 diff 性**这些维度上逐格填满，每格带证据。
2. **懒加载到底怎么做（本次调研核心之一）** —— 粒度（整表 / 分片 / 行 / 列）、索引与偏移表的设计、首次访问的卡顿（hitch）从哪来、缓存与驱逐策略、以及**懒加载与「不可变快照 + 原子激活」这对语义怎么共存**。
3. **表变大之后怎么活下去（本次调研核心之二）** —— 压缩方案与随机访问的矛盾怎么解、紧凑编码能省到什么程度、常驻内存的真实构成（尤其托管运行时下「每行一个对象」的代价）、以及表规模增长的**拐点在哪、征兆是什么**。
4. **AI 友好的配表形态（本次调研核心之三，且工业界证据最薄）** —— AI 能不能直接读写表、通过什么接口、校验失败怎么反馈回去形成闭环、AI 改坏了怎么回滚与审计。**这一块公开案例可能很少，查不到就诚实说查不到，然后给出「基于相邻领域证据的可行形态推演」并标 `Estimated`——绝对不要拿零星博客当行业共识。**
5. **每一个设计背后的那个坑** —— 不要 API 罗列。为什么大量工具最终都从「Excel 直接当权威源」退到「Excel + 文本镜像」？为什么按需加载的表几乎都要配一张离线索引？为什么整表压缩在懒加载场景下几乎必错？**每个设计背后都有一个具体的、可复述的事故，把那个事故挖出来**——这比记住格式名有价值一百倍。
6. **渐进路线的不变量清单** —— 委托方打算「JSON 先行、二进制后上」。这条路线里**哪些东西必须第一天就定死，否则第二期根本换不动**？这一条对决策的价值极高，单列成节。

最终这份报告要能回答一个问题：**在一个 Rust 内核 + C# 托管层、要跑在浏览器 WASM 上、要求确定性与状态哈希、表会长到很大的引擎里，配表管线应该长成什么样；哪些决定必须现在做，哪些可以推迟。**

#### 3.2 已冻结的配表契约（**不要评审对错，只判断实现可行性**）

一张编译后的配置表，其契约字段已经冻结为：

- `tableId`、`schemaVersion`、`configRevision`、`generatedAt`、`sourceHash`、`columns`、`rows`、`activation`、可选 `signature`。
- **列描述必填**：`name`、`type`、`required`，可选 `minimum` / `maximum` / `enumValues` / `refTarget` / `defaultValue`。
- **列类型系统已冻结**：`bool`、`i32`、`i64`、`u32`、`u64`、`f32`、`f64`、`string`、`enum`（闭集）、`ref`（引用另一张表的行 ID）。
- **校验规则已冻结**：逐格类型检查；范围越界拒绝；未知列拒绝；缺必填列拒绝；引用目标不存在拒绝；默认值可以填补缺失的**可选**单元格，但**不能补造缺失的必填单元格**；生产环境激活未签名拒绝。
- **激活模式已冻结**：`DevelopmentHotLoad`（开发可热载）与 `ProductionSignedSwitch`（生产必须带签名的版本切换）二选一。
- **运行时持有形态已冻结**：Config Port 同时持有 **Staged 与 Active 两份不可变配置快照**，以 `ConfigRevision` 标识；生产切换**只在 Tick Barrier 原子发生**。
- **层级覆盖顺序已冻结**：Engine → Platform → Server → Product → Environment → User/Session。
- **Secret 与普通配表分离**已冻结。
- **二进制容器头已冻结（与存档同族）**：Magic、SchemaVersion、Length、Hash、Checksum、Compression、可选加密元数据。反序列化必须先校验头、长度、压缩比与边界再 materialize，且要有最大消息 / 最大分配 / 最大解压比限制。
- **Canonical 序列化已冻结**：参与 Hash 的编码必须按稳定顺序产生确定字节，不得依赖运行时对象图或遍历地址。
- 文本导出（JSON 等）**允许作为诊断用途**，但不作为高性能权威存储。

#### 3.4 已知待解的硬问题（调研时请特别留意同类方案的答案）

1. **懒加载与「不可变快照」的语义冲突**：如果一张表还没被加载，它属于 Staged 还是 Active？切换 Revision 时，正在懒加载中的表怎么办？「不可变快照」在按需加载下还成不成立？
2. **双份快照 × 大表 = 内存翻倍**：Staged 与 Active 并存时，未变更的表能不能共享同一份内存？靠什么保证共享是安全的？
3. **浏览器 WASM 的三重约束**：无 mmap、包体敏感、内存上限——按需加载只能走网络（HTTP Range？IndexedDB 缓存？），这对格式设计有什么硬性要求？
4. **Rust 与 C# 读同一份二进制**：能不能双方都零拷贝直读？对齐、字节序、字符串表示怎么统一？谁负责校验？
5. **浮点的跨端确定性**：Excel 里的十进制数 → `f32` / `f64` → 两端解析——这条链路上哪里会产生不一致？定点化是不是唯一正确答案？
6. **可见性切分与 Hash 的矛盾**：客户端不该拿到某些表/列（掉率、AI 参数、服务器公式），但两端又要能校验配置一致性——**只持有子集的一端，怎么算出一个可对账的 Hash？**
7. **代码生成产物的体积**：几百上千张表生成的强类型访问器，在 WASM 包体与 AOT 启动时间上的代价有多大？
8. **Excel 作为权威源**：二进制文件不可 diff、合并冲突无解、类型保真差（前导零、科学计数法、日期自动转换）——工业界怎么缓解，还是干脆放弃？
9. **AI 改表的闭环**：AI 通过什么接口写、校验失败怎么把错误喂回去、改坏了怎么回滚、怎么审计「这一行是谁改的、为什么改」。
10. **规模拐点**：多少张表 / 多少行 / 多少 MB 时，全量加载会崩？懒加载会开始出现可感知卡顿？

- **编码级省空间手段全清单**，每条给出适用条件与实际收益量级：

#### H. Schema 定义、类型系统与演进

- **Schema 写在哪**：表头行内联 / 独立 schema 文件 / 代码内声明 / 数据库元数据。四种的可读性、可 review 性、工具支持差异。
- **类型系统能力对照**：主流配表工具支持的类型集合（标量、枚举、引用、**容器类型：数组 / 字典 / 嵌套结构**、可空、多态/变体）。**画像目前只有标量 + enum + ref，没有容器与嵌套——工业界普遍有吗？没有会怎样（提示方向：多语言文本、掉落列表、条件数组这类天然是列表的数据怎么在只有标量列的表里表达）。这是缺口分析的重点之一。**
- **默认值语义**：默认值写在 schema 还是数据里？空单元格、空字符串、显式 null 三者怎么区分？**这是配表最容易出隐性事故的地方之一，重点挖案例。**
- **Schema 演进**：加列 / 删列 / 改类型 / 改枚举值 / 改默认值，各自的兼容规则与迁移做法。旧存档引用旧表结构怎么办。
- **多态与继承**：一张表里的行有不同形态（不同类型的道具有不同字段）——工业界的表达方式（宽表留空 / 分表 / 类型列 + 变体 / 侧表）与各自代价。
- **本地化**：文本表的组织方式、按语言切分与懒加载、与主表的引用关系。

#### I. 引用完整性、ID 与索引

- **ID 体系**：字符串 ID vs 整数 ID vs 两者并存（可读 ID 编译成整数）。**编译期把字符串 ID 转成稠密整数**这个手法的收益（内存、比较速度、索引）与代价（可调试性、diff 可读性、跨版本 ID 稳定性）。
- **ID 的稳定性与回收**：删掉一行后 ID 能不能复用？旧存档 / 旧客户端引用了已删除的行怎么办？工业界的墓碑与弃用标记做法。
- **引用图**：跨表引用的校验时机（编译期全图校验 vs 运行时首次访问校验）、循环引用检测、**懒加载下的引用完整性怎么保证**（引用了一张还没加载的表，是同步加载还是报错？）。
- **ID 分配与冲突**：多人并行配表时的 ID 冲突，工业界怎么防（号段分配、命名空间前缀、编译期检测）。
- 运行时查询能力的边界：只按主键取行够不够？条件筛选、多列索引、范围查询在配表场景下的实际需求与实现代价。

#### J. 确定性、Hash 与两端一致性

- **配置参与状态哈希**：哪些引擎公开做过「配置版本参与一致性校验」？做到哪一层（整包 Hash / 逐表 Hash / 逐行 Hash）？
- **Canonical 编码的坑**：同一份数据的多种合法编码（浮点的多种表示、map 顺序、可选字段的省略与显式默认、字符串规范化形式）——**每一条都是 Hash 不一致的来源，逐条列出并给出规避手法。**
- **两端持有不同子集时怎么对账**（呼应 3.4 的硬问题 6）：分层 Hash / Merkle 树 / 只对公共子集算 Hash / 各端各自 Hash 后交换清单。**工业界有没有先例？没有就明说，并给出可行方案的推演（标 `Estimated`）。**
- **浮点与确定性**：从策划填的十进制到运行时的二进制浮点，这条链上的每一次转换可能引入的差异；定点化的实际做法与代价。
- **加载顺序无关性**：懒加载导致不同的加载顺序，会不会影响求值结果或 Hash？怎么设计才能保证无关。
- **Replay 与配置**：回放一段历史时，必须用当时的配置版本——工业界怎么把配置版本钉进回放数据？旧版本配置的长期保存与可用性。

#### K. 热更、Revision 与激活语义

- **热更配置的工业界形态**：整包替换 / 增量补丁 / 单表替换 / 远端配置服务（feature flag / 远程参数）。各自的生效延迟、回滚能力、审计能力。
- **激活的原子性**：切换瞬间正在读表的代码看到什么？工业界的做法（双缓冲、读写锁、Epoch / RCU、帧边界切换）。
- **正在被引用的旧 Revision**：一个已经取到旧 Revision 数据的对象，在切换后还持有旧值——这是 bug 还是特性？工业界怎么规定。
- **回滚**：切回上一个版本的实际难度；有状态的副作用（已经按新配置发出去的奖励）怎么办。
- **签名与信任链**：生产配置签名的实际做法、密钥管理、验签失败的降级策略。
- **与懒加载的交叉（重点）**：切 Revision 时，尚未加载的表按新版本加载、已加载的表按旧版本——**这种「混合版本」状态是所有懒加载 + 热更系统的经典 bug 源。工业界怎么防？**（提示方向：整代切换 + 旧代延迟释放、Revision 打进每个表的句柄、访问时校验代际。）

#### L. 访问 API 形态：代码生成 vs 反射 vs 零拷贝 view

- 三种形态逐个剖析：**生成强类型访问器**（`ItemTable.Get(id).Damage`）、**通用行/字段访问**（`table.GetRow(id).GetInt("damage")`）、**零拷贝 view**（直接在缓冲区上按偏移取值）。维度：类型安全、重构友好度、IDE 支持、**产物体积**、启动时间、访问性能、AOT 兼容性。
- **代码生成的体积问题（重点）**：几百上千张表 × 每表一个类 + 访问器 + 索引，在 IL 体积、WASM 包体、AOT 编译时间、启动时的类型初始化上的实际代价。**有没有公开的量级数据？团队怎么缓解（按需生成、合并生成、只生成常量与索引）？**
- 生成物的工程属性：入不入库、可不可 diff、与源表的一致性怎么保证（CI 校验？）、生成失败怎么办。
- 热路径访问性能：一次「按 ID 取一行的一个字段」在三种形态下的开销构成。**有实测就引用条件，没有就给成本模型。**
- 空值 / 缺失值在 API 层面怎么暴露（返回默认值？可空类型？显式 `TryGet`？）——**这是运行期空引用事故的主要来源之一。**
