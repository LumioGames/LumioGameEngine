## 提示词正文

你是一名资深的游戏服务器 / 网络引擎架构调研员。任务是把 **Unreal Engine 的 Dedicated Server（专用服务器，下称 DS）架构**吃透——它的设计思想、不变量与取舍——产出一份能直接作为架构决策输入的深度报告。

### 1. 我们到底想从这次调研拿到什么

不要写成使用手册（「如何打包 DS」「怎么配置端口」「怎么上传到某托管平台」）。要写成**架构解剖**：机制 → 它解决的根本问题 → 设计取舍 → 隐含前提 → 失效模式 → 代价。

一句话目标：**UE 在「做一个可上线的专用服务器」这件事上，究竟想清楚了哪些问题、用什么机制解决、付出了什么代价、哪些是本质、哪些是历史包袱。**

具体想拿到五样东西：

1. **一张完整的服务器解剖图** —— 从「一个客户端的 UDP 包打到服务器网卡」到「这个玩家看见别人挖了一个方块」，中间每一层是什么、在哪个线程 / 哪一帧 / 哪个阶段发生。**要能画成两张图：一次连接建立的消息序列图，一次服务器复制循环的流程图。**
2. **每一个设计背后的那个坑** —— 不要 API 罗列。为什么可靠性建在 bunch 层而不是包层？为什么复制是「服务器为每个连接维护影子状态再逐属性 diff」这么贵的做法，而它撑了二十年？为什么 Epic 最后还是要造 Iris 重来一遍？**每个设计背后都有一个具体的、可复述的事故，把那个事故挖出来**——这比记住类名有价值一百倍。
3. **三个最高优先级重章（本次调研的核心）：**
   - **复制模型**（E 章）：权威角色三态、属性复制的语义边界、RPC 的可靠性与顺序保证、poll-and-diff 与 push model 的代价差、Iris 承认了旧系统的哪些结构性问题。
   - **兴趣管理与带宽调度**（F 章）：把「复制」理解成**一个带字节预算的调度问题**而不是「把状态发出去」——这个视角转变在 UE 代码里落在哪些具体机制上。
   - **反向教训**（L 章）：UE DS 的结构性缺陷清单，每条给成因与后果，不许写成情绪化的吐槽。
4. **「引擎给了什么 / 你必须自己写什么」的准确边界** —— UE DS 有大量能力其实是空接口或社区惯例（编排、扩缩容、持久化、匹配、账号、反作弊、断线重连、不停服更新）。**每一处都要讲清边界，不要把「社区常见做法」说成「引擎内置」。**
5. **可移植性判定** —— 对提炼出的每一条设计原则，判定它在第 3 节那张画像下是「可直接借鉴 / 需改造后借鉴 / 不适用」，并说明理由与代价。

最终这份报告要能回答一个问题：**UE 的服务器设计里，哪些是换一个引擎、换一种语言、换一套对象模型仍然成立的「本质」，哪些只是 UE 的反射系统、Actor 模型、蓝图与向后兼容包袱长出来的「偶然实现」。**

委托方另有四份**并行进行**的调研。本次调研管的是**「进程 / 传输 / 连接 / 会话 / 复制调度」这一层**，不碰上层语义：

### 3. 目标环境画像（用于判断可迁移性；自包含，不需要查任何代码）

委托方的引擎与 UE 差异很大，做可迁移性判断时**以这张画像为准**。

| 维度 | 目标环境的形态 |
|---|---|
| 项目形态 | 自研游戏引擎的**体素大世界**。服务器权威模拟，客户端跑只读副本世界。近期目标：多个**浏览器**客户端登录同一个体素世界联机，挖 / 放方块实时互见。 |
| 语言与运行时 | **Rust 原生宿主**负责进程 / 网络 / 会话 / 传输；**C# 托管层**承载 Gameplay 语义；两层之间是稳定 ABI。**没有 UObject、没有引擎级 GC 对象图、没有蓝图 VM、没有 Actor 复制模型、没有 C++ 反射系统。** |
| 客户端形态（**硬约束**） | 客户端跑在**浏览器**里（.NET WASM）。**拿不到原生 UDP socket**：只能用 WebSocket / WebTransport / WebRTC DataChannel 这一类受限传输，且受同源策略、TLS 强制、连接数限制约束。**评估任何传输设计时必须带上这一条**——UE 的整套网络栈建立在「我有一个原生 UDP socket」这个前提上。 |
| 帧模型 | **固定步长、分相位推进的确定性逻辑 Tick**；一帧内有**唯一的提交点**；提交点之前的写入对复制与快照不可见，提交点之后重复执行必须幂等。 |
| 确定性诉求 | 需要可复现的求值顺序与**可计算的状态哈希**，用于回放、对账与崩溃恢复。**同一串输入必须产出同一状态**（Rust 权威实现与 C# 参考实现之间还要做差分测试）。 |
| 状态存储 | **ECS 是被复制的 Gameplay 状态的唯一权威存储**。世界实例分 `Authority` / `Replica` 两个角色，**各自独立的存储与实体命名空间**，通过身份映射对应。 |
| 契约模型 | **契约先行**：线协议由 Schema 生成，**字段集封闭**，客户端与服务端都不得各自扩展载荷；序列化有**规范化字节**要求（同一状态在任何合规编码器上产出逐字节相同的结果，用于哈希、校验与迁移）。 |
| 权威与预测 | 服务器校验并提交；客户端只能在**有界的预测窗口**内预测。ECS 状态、Ability 状态、体素覆盖层属于**同一个确认 / 回滚单元**，要么一起确认要么一起回滚。 |
| 故障模型 | Tick 内故障 **fail-stop**：不做字段级撤销，**整帧作废**，从快照 + 日志重建。 |
| 世界与流送 | 三维 Chunk 分块体素世界，存在**大规模写入**与区块流送；chunk 有驻留预算与驱逐栅栏。**铁律：缺失的 chunk 永远不等于空世界**，未加载 / 加载中 / 不可用必须显式上报，不得当空气返回。 |
| 持久化 | 快照 + WAL（前后哈希链）；写盘走 staging / 校验 / fsync / 原子激活，保留上一个有效检查点；恢复只重放**已认证且已提交**的记录。 |
| 发布与运维 | 发布目录按「产品 id + 发布 id」路由，**一个进程只装一个 Release**；当前要求**服务端与客户端 Release 精确匹配**。**多版本共存、滚动更新、会话排空、崩溃恢复**是明确的运维诉求。 |
| **尚未冻结** | **传输与编解码供应商、RPC / 消息分发模型、鉴权线协议、断线重连与恢复令牌、滚动更新的排空策略、耐久级别分档**——可靠通道与不可靠通道都还在桌面上。**本次调研的结论会直接影响这几项选型。** |
| 明确推迟 | 线上运营发布本身（部署、灰度、CDN、运维流程）；匹配、账号体系、反作弊的具体实现。**接口面要预留，实现不展开。** |

#### 已知待解的硬问题（调研时请特别留意 UE 的答案，哪怕答案是「UE 也没解决」）

1. **固定步长 vs 可变步长**：UE 服务器是非固定步长的，这个选择渗透到了多少地方？一个要求确定性的引擎，能从 UE 的网络栈里继承多少东西？
2. **浏览器传输**：UE 的可靠性、分片、拥塞、握手全建在原生 UDP 上。剥掉 UDP 之后，它的哪些分层还成立、哪些直接塌掉？
3. **契约封闭 vs 反射驱动**：UE 的属性复制靠 C++ 反射逐字段 diff。一个「Schema 生成 + 字段集封闭 + 规范化字节」的模型，能不能达到同样的表达力？会丢什么？
4. **复制成本模型**：`对象数 × 连接数` 的结构性成本，UE 用相关性 / 休眠 / ReplicationGraph / Iris 四代方案对付它。这四代分别承认了前一代的什么问题？
5. **体素级大规模写入**：Actor 属性复制这套东西根本不是为「一秒钟改几万个体素」设计的。UE 在大世界流送上的方案，有没有任何一部分能迁移到 chunk 流送上？
6. **断线重连与会话恢复**：UE 内置到底有没有？没有的话，生产项目补的那一层长什么样、挂在哪个钩子上？
7. **不停服更新与版本共存**：UE 几乎完全没有。业界（含非 UE 项目）在这件事上的成熟形态是什么？
8. **回放**：UE 用「录制即写给一个假连接」复用了复制管线。这条复用路径的架构价值与限制分别是什么？对一个已经有状态哈希与 WAL 的引擎，还值不值得抄？
9. **服务器权威的信任边界**：UE 默认信任客户端的东西有哪些（移动是最大的一块），这个默认值的历史原因与作弊面。
10. **可观测性**：一个网络服务器最少需要哪几类观测量才能定位问题？UE 提供了哪些、缺哪些？

**注意**：与常见的「只做研究、不做评价」不同，**本次调研明确要求你在收尾章（M 章）给出判定与建议**。但中间各章必须是有证据的事实调研，不是意见输出——**观点只能出现在 M 章，且每个观点必须挂在前面章节的证据上。** 同时**不要评审第 3 节那张画像的对错、也不要建议改它**：你的产出是「UE 是怎么做的 + 这个做法在这套约束下能不能成立 + 代价是什么 + 缺了什么」。

#### E. 复制模型（**最高优先级重章之一**）

这一章要写到能让人照着重新设计的程度。

- **权威与角色模型**：本地角色 / 远端角色的三态（权威 / 自治代理 / 模拟代理），它如何成为整套网络代码的地基；**这三态在业务代码里的实际渗透程度**。
- **Actor 复制的开关与生命周期**：通道的开 / 关如何与对象生命周期解耦；初始复制、临时对象（一次性生成的特效类对象）、tear-off 的语义；**销毁的复制**（客户端怎么知道一个对象没了、相关性丢失与真正销毁怎么区分——这是有名的坑）。
- **属性复制**：声明方式、复制条件（仅所有者 / 跳过所有者 / 仅初始 / 仅模拟 / 自定义等，**逐个给准确名称与语义**）、变更通知回调的触发时机。
- **poll & diff 模型**：服务器为每个连接维护影子状态、逐属性比较、只发变化。**它的 CPU 成本从哪来（成本公式写出来）？push model（脏标记驱动）解决了什么、迁移成本是什么、为什么不是默认？**
- 子对象与组件复制、可复制的非 Actor 对象、**增量数组序列化器**（增删改回调）的设计与它的失败模式（乱序、丢包、溢出）。
- **语义边界（必须讲透）**：属性复制是「最新值获胜」的最终一致性，**不保证中间值、不保证与 RPC 的相对顺序**。这条语义如何**反向约束**了 gameplay 代码的写法？哪些游戏逻辑因此根本不能用属性复制表达（必须改用 RPC 或事件）？**给出具体例子。**
- **RPC**：三种方向（Server / Client / Multicast）× 可靠 / 不可靠；服务器 RPC 的校验钩子；对不相关对象调用 RPC 会发生什么；**可靠 RPC 泛滥的后果**（队列溢出 → 断连）。
- **顺序保证的完整清单**：哪些东西之间有顺序保证、哪些没有。**这张表比任何描述都有用，务必列出来。**
- **Iris（UE5 的新复制系统）**：它改变了什么——状态驱动而非轮询、过滤与优先级的职责分离、增量压缩、与旧系统的共存与迁移路径、当前成熟度。**它承认了旧系统的哪些结构性问题？**——这一小节价值极高，因为它是 Epic 自己写的「旧设计错在哪」。
- **一句话总结**：UE 的复制哲学是什么？（同步状态？同步事件？混合？在哪里选了哪一种、为什么。）

#### F. 兴趣管理与带宽调度（**最高优先级重章之二**）

- **相关性（relevancy）判定**：距离剔除、始终相关、所有者相关、自定义判定、相关性超时；**判定发生在哪一帧的哪个阶段、代价多大**。
- **优先级排序与饥饿避免**：优先级如何累积，长期低优先级的对象最终会怎样。
- **每连接带宽预算**：服务器一帧内如何「排序 — 填充 — 截断」；**超预算的对象被推迟会造成什么可观测现象**（玩家眼里看到什么）。
- **休眠（dormancy）机制**：几种休眠态、唤醒与刷新的触发、它对 CPU 的意义、忘记唤醒的经典 bug。
- **ReplicationGraph**：用空间 / 分类节点结构替代「对象数 × 连接数」的暴力扫描；常见节点类型；**它把成本从运行时挪到了哪里**（答案是手工调优——把这个代价写清楚）。
- **重点回答一**：把「复制」理解成**一个带字节预算的调度问题**而不是「把状态发出去」——这个视角转变在 UE 代码里体现在哪些具体机制上？**这是本章最有价值的一段。**
- **重点回答二（与 ECS 专项的交界）**：UE 的「相关性 + 休眠 + 优先级」，与「AOI 进出即实体生命周期事件（`OnEnterScene` / `OnLeaveScene`）」这种模型，是不是同一件事的两种表达？**差在哪？** 具体地：UE 有没有「进入 / 离开视野」这种**离散事件**语义，还是只有「这一帧相不相关」这种**连续判定**？把 AOI 进出绑成生命周期钩子，UE 的经验说明会踩什么坑（抖动、边界反复进出、状态重建成本）？

- 服务器端延迟补偿（回溯命中判定）：UE 内置了多少、项目通常要自己补什么。
- **客户端权威的边界**：哪些状态引擎默认信任客户端（移动是最大的一块），这个默认值的历史原因、作弊面、以及社区的加固手法。
- **重点回答**：预测 / 和解要成立，对「输入表示」「状态可重放」「步长一致」提了哪些硬前提？**UE 在通用 Actor 层面为什么做不到、只能在移动组件这个特例里做到？** 通用网络预测框架为什么这么多年还没成为一等公民？——**这一问直指第 3 节画像的核心诉求，挖到底。**

#### H. 录像与回放

- 回放通过**复用同一条复制管线**实现（录制即「写给一个假连接」）、检查点机制、流式存储抽象。
- **重点回答**：这条「网络序列化 = 录像序列化」的复用路径，架构价值是什么？限制是什么（只能录到复制出去的东西 / 无法完全复现服务器内部状态 / 与非确定性 tick 的关系）？

#### I. 服务器侧的世界流送与大世界

- 大世界方案（World Partition 一类）的**服务器端**行为：服务器是否 / 如何流送与卸载区域、数据层的服务器语义、**服务器卸载了一块地之后那块地上的对象怎么办**。
- 流送与相关性的耦合：一个对象「没加载」和「不相关」在协议层是不是同一件事？客户端怎么区分？
- **重点回答（对体素引擎最关键）**：UE 这套东西的粒度是 **Actor / 关卡**。一个「一秒钟可能改几万个体素、chunk 是一等公民」的世界，UE 的哪些机制还成立、哪些完全不适用？**有没有任何公开的体素类项目在 UE 上做到了大规模方块同步？他们怎么绕过 Actor 复制的？**（这条查不到就诚实写查不到，不要编。）

#### J. 可观测性与运维（**接口面盘点，不做选型**）

- 网络性能观测手段：统计面板、网络 profiler、trace、相关性调试命令、日志分类。**逐个给准确名称，拿不准标「名称待核」。**
- **一个网络服务器最少需要哪几类观测量**才能定位问题（带宽构成、每对象复制成本、丢包重传、通道队列深度、tick 超时）？UE 提供了哪些、缺哪些？
- DS 的日志、崩溃处理、headless 运维形态。
- **UE 明确不提供什么**：进程编排、扩缩容、健康检查、持久化 / 数据库、匹配、账号、反作弊——在线服务接口层只是抽象，**真正的实现挂在哪个位置、以什么形状挂**。
- **多版本共存 / 滚动更新 / 会话排空 / 不停服更新**：UE 内置支持到什么程度（预期答案是「几乎没有」——那就把「没有」这件事本身讲清楚：为什么没有、它假设了什么运维形态、生产项目补的那一层长什么样）。
- 多进程 / 多房间部署的常见拓扑，以及引擎对此的（不）支持。

#### K. 安全与信任边界

- 服务器权威作为唯一信任根；RPC 参数校验的机制与其局限。

- 客户端能看到什么：**属性复制的可见性控制粒度**（能不能做到「这个字段只发给所有者」）、以及打包后客户端里还剩多少服务器信息。

#### L. 反向教训（**必须单列一章，不许只写优点**）

每条给**成因 + 后果 + 社区的规避手法**，不要写成情绪化吐槽。至少覆盖：

- 复制成本随 `对象数 × 连接数` 增长的结构性问题，以及 ReplicationGraph 的手工调优负担。
- 属性轮询比较的 CPU 成本；蓝图侧的网络开销。
- 可靠队列溢出导致断连的脆弱性。
- 非固定步长带来的不可复现性。

- 断线重连没有内置方案。

#### M. 精髓提炼与可迁移性评估（**必写的收尾章，验收重点**）

前面是资料，这一章是结论。

**M.1 十到十五条「可迁移的设计原则」**，每条严格按五段式写：

1. **原则**（一句话，抽象表述，**不带 UE 术语**）
2. **UE 中的体现**（具体机制 + 证据坐标）
3. **它解决的根本问题**（没有这条原则会发生什么）
4. **隐含前提**（例如：依赖原生 UDP / 依赖非确定性 tick / 依赖 Actor 对象模型 / 依赖单进程单世界 / 依赖 C++ 反射系统）
5. **前提不成立时是否仍然成立**（**这是判断可移植性的关键，不许略过**）

**M.2 本质 vs 历史包袱**，各列一节：

- **本质**：换一个引擎、换一种语言、换一套对象模型仍然成立的设计。
- **历史包袱 / 偶然实现**：因为 UE 的反射系统、Actor 模型、蓝图、向后兼容包袱才长成这样的部分。

**M.3 可迁移性判定表**：对 M.1 的每一条原则出一行。

| # | 原则 | 判定 | 理由 | 若「需改造」：改造点 | 若「不适用」：冲突在哪 | 优先级 |
|---|---|---|---|---|---|---|

- 判定三选一：**可直接借鉴** / **需改造后借鉴** / **不适用**。
- 每条「可直接借鉴」**必须同时写出它的风险或代价**，不许只写优点。
- 每条「不适用」**必须指出具体冲突**（例如「依赖非确定性 tick，与固定步长确定性要求冲突」「依赖原生 UDP，浏览器客户端拿不到」）。
- 优先级 P0 / P1 / P2 并说明理由（P0 = 不借鉴会导致架构性返工）。

**M.4 完整性缺口清单**：对照第 3 节画像，逐条指出「成熟的服务器架构普遍具备、而这张画像里压根没提到」的能力与语义。每条带四要素：**谁有 + 怎么做 + 不补会怎么炸 + 分级（P0/P1/P2）**。宁可多列，不要漏。

**M.5 UE 没有解决、委托方必须自己解决的问题清单**：如确定性重放、版本共存、契约封闭性、断线恢复、体素级大规模写入的复制、浏览器传输。每条说清「为什么 UE 没解决」。

**M.6 UE 踩过的坑中，最该提前规避的五条**：每条给规避**方向**（只给方向，不要展开设计）。
