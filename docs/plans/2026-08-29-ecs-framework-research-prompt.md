### 1. 我们到底想从这次调研拿到什么

委托方**已经有一套自研 ECS 的设计雏形**（第 3 节的画像），现在要做的不是从零选型，而是**重新审视这套框架的完整性**：同类框架都解决了、而我们还没想到的问题是什么；我们已经想到的部分，别人是怎么做的、踩过什么坑。

具体想拿到四样东西：

1. **同类思路的谱系与坐标** —— 「组件自带逻辑、组件之间协作、前后端共用同一套实体定义」这条路线，市面上有谁在走？它在 ECS 谱系里的**准确位置和学名**是什么？它与「正统数据导向 ECS」的分水岭到底在哪一条线上？走这条路的人各自得到了什么、付出了什么。
2. **每一个设计背后的那个坑** —— 不要 API 罗列。为什么 Unity 要把 `Awake` 和 `Start` 分成两个钩子？为什么大量网络框架要给 AOI 进出单独设事件而不是复用 Enable/Disable？为什么结构变更几乎都要延迟到提交点？**每个设计背后都有一个具体的、可复述的事故，把那个事故挖出来**——这比记住接口名有价值一百倍。
3. **两个最高优先级重点（本次调研的核心）：**
   - **属性同步**：「声明即同步」这件事，工业界到底有几种做法，各自的脏标记粒度、通知时机、带宽代价与失败模式是什么。
   - **AOI / 兴趣管理**：进出 AOI 的语义、事件、抖动抑制、与实体生命周期的绑定方式——以及「把 AOI 进出做成实体生命周期钩子」这个决定，先例是谁、后果是什么。
4. **完整性缺口清单** —— 这是本次调研**最核心的交付物**。对照第 3 节的画像，逐条指出「同类框架普遍具备、而这张画像里压根没提到」的能力与语义。宁可多列，也不要漏。

最终这份报告要能回答一个问题：**这张画像离一套能扛住海量实体、前后端共用、可回放可对账的生产级框架，还差哪些东西；这些差距里哪些是必须现在补的，哪些可以推迟。**

委托方另有四份**并行进行**的调研：GAS 专项、DS 服务器专项、配表管线专项、体素地图存档专项。与 GAS 那份的边界最需要注意——本次调研**不要展开技能 / 效果 / 数值修饰器的内部机制**，只关注两处接口面：

### 3. 目标环境画像（用于判断可迁移性；自包含，不需要查任何代码）

这是委托方自研框架的当前设计雏形。做对比与缺口分析时以这张画像为准。

| 维度 | 目标框架的形态 |
|---|---|
| 定位 | **完全自研的 ECS**，不是 Unity DOTS，也不是任何现成 ECS 库的封装。E / C / S 三个字母沿用，语义自定义。 |
| 编程范式 | **不是面向数据设计（DOD）**。组件不是纯数据块，**组件自带逻辑**；核心手法是「把对象的能力拆成组件，组件与组件之间协作」。System 存在，但不是唯一的逻辑容器。本质上是**面向对象逻辑 + 组件组合**。 |
| 语言与运行时 | 托管语言（C#）承载 Gameplay，底层有原生内核。**没有 UObject / 引擎级 GC 对象图、没有蓝图 VM、没有 Actor 复制模型、没有 Unity GameObject。** |
| 前后端关系 | **同一套 Entity / Component 定义前后端共用**。一个实体在服务器与客户端**同时存在**、同时持有组件。两端允许有不同字段甚至不同实体子集（非对称组件），但实体类型与身份是同一个概念。 |
| 容器 | 一切实体归属于一个 `World`。服务器权威 World 与客户端投影 World 是**各自独立的存储与实体命名空间**，通过身份映射对应。 |
| 实体身份 | 网络身份是不透明定长值，**不是数组下标**；World 内的本地身份是 `Index + Generation`，只在本 World 有效。销毁产生墓碑，同一会话内**不复用**已销毁身份；客户端预测创建的实体使用独立命名空间，服务器确认时做重映射。 |
| 实体创建 | **先声明实体类型，创建时按类型绑定一组组件**（组件在创建时就建好）。预期是**海量创建**——创建路径的延迟与分配量是一等性能指标，「逻辑创建要非常快」是硬需求。 |
| 生命周期 | 固定六个钩子：`Awake` → `Start` → `OnEnterScene` → `OnLeaveScene` → `OnDisable` → `OnDestroy`。其中 **`OnEnterScene` / `OnLeaveScene` 由 AOI 驱动**：实体进入 / 离开**服务器 AOI 或客户端 AOI** 时自动进出该状态。 |
| 属性同步 | **声明即同步**：在实体 / 组件上一开始声明的属性变量会自动在服务器与客户端之间同步，业务代码不手写同步调用。服务器权威侧发生变化即推送到本地客户端。 |
| 数值属性 | 实体上挂一组 `Attribute`（生命、攻击、移速这类数值）。服务器侧变化时更新并同步到客户端。 |
| 基础组件 | `Transform` 组件是**整个架构最核心的组件**；`Model` 组件负责挂载模型等表现资源；能力以组件形式挂载（例如挂一个 GAS 组件，该实体就获得技能 / 效果能力）。 |
| 帧模型 | 逻辑 Tick 分相推进，一帧内有**唯一的结构提交点**；结构变化（创建 / 销毁 / 增删组件）经命令缓冲延迟到提交点统一应用，不在业务相内立即生效。 |
| 权威与预测 | 服务器权威；客户端只能在**有界窗口**内预测。ECS 状态与其它子系统状态属于**同一个确认 / 回滚单元**，要么一起确认要么一起回滚。 |
| 故障模型 | Tick 内故障 **fail-stop**：不做字段级撤销，整帧作废，从快照 + 日志重建。 |
| 确定性诉求 | 需要可复现的求值顺序与**可计算的状态哈希**，用于回放、对账与崩溃恢复。 |
| 分层原则 | 框架层拥有实体 / 组件 / 查询 / 生命周期 / 同步 / AOI 的通用机制；内容层只拥有具体组件类型、数值与表现资源。 |
| **尚未选定** | **Storage 的内部表示没有冻结**——Archetype、Column、Sparse Set 还是别的，都在桌面上；目前只冻结了 Entity / Component / Query 的语义。**本次调研的结论会直接影响这个选型。** |

#### 已知待解的硬问题（调研时请特别留意同类框架的答案）

1. 六个生命周期钩子的精确语义与触发时机——尤其 `Awake` 与 `Start` 的分界依据、`OnDisable` 里的「禁用」到底禁掉了什么。
2. **服务器 AOI 与客户端 AOI 是不是同一个概念**（服务器 AOI ≈ 谁能看见我；客户端 AOI ≈ 我加载了谁），把两者的进出塞进同一对钩子会不会出问题。
3. 「声明即同步」的脏标记粒度、变更通知时机、带宽预算与可见性裁剪。
4. Attribute 的权威计算位置：服务器算完同步**结果**，还是同步**输入**让客户端自己算。
5. 组件之间的依赖声明、初始化顺序，以及跨组件引用在对方被移除后的失效检测。
6. `Transform` 的父子层级、脏标记传播、局部 / 世界变换，以及它的网络表示与量化。
7. 海量实体创建路径的分配行为与缓存行为（托管运行时下的 GC 压力）。
8. 结构变更延迟到提交点，与生命周期钩子触发时机之间怎么对齐（`Awake` 在提交点之前还是之后）。
9. Storage 表示的选型。

**注意**：与常见的「只做研究、不做评价」不同，**本次调研明确要求你在收尾章给出缺口判断与建议**（第 4 节 P 章）。但中间各章必须是有证据的事实调研，不是意见输出——**观点只能出现在 P 章，且每个观点必须挂在前面章节的证据上**。

#### A. 谱系、源流与流派分野

- Entity-Component 思想的源头：早期把「游戏对象 = 组件容器」讲清楚的那批分享与文章（含 GDC 分享、博客系列），能查到多少写多少，给准确标题与年份。
- **「ECS」这个词的含义漂移史**：从「实体系统」到「数据导向 ECS」，中间发生了什么，为什么今天说 ECS 大多数人默认指数据导向那一支。
- **三个流派的分水岭，逐条画清楚**：
  - **纯数据导向 ECS**（组件是 POD、逻辑全在 System、按 Archetype / 列存储组织）
  - **对象组合式组件模型**（组件自带逻辑、组件间直接协作，如经典引擎的 GameObject / Actor-Component 体系）
  - **中间形态**（保留组件逻辑但引入实体存储、查询与生命周期管理的那一批框架）
  - 每一派回答清楚：**它为了什么而存在？它放弃了什么？它的性能上限由什么决定？**
- **第 3 节画像属于哪一派**？给出定位判断和理由。市面上还有谁在同一格子里？
- 「组件带逻辑」这条路被正统 ECS 阵营批评的**具体技术理由**（不是立场，是理由），以及被批评方的公开回应。

#### B. 前后端共用同一套实体定义的工程形态（画像的核心特征之一）

- **谁真的做到了「前后端共用」**？逐个列出，并说清**共用的到底是哪一层**：
  - 只共用 Schema / 定义文件（两端各自生成代码）
  - 共用类型定义 + 部分逻辑
  - 共用整套 Gameplay 逻辑（同一份代码在两端跑）
- 三种共用程度各自的收益与代价：**版本一致性、客户端可见性与作弊面、平台差异（AOT / 裁剪 / 反射）、热更新、编译期与包体代价**。
- **非对称组件怎么表达**：服务器有而客户端没有的字段 / 组件 / 甚至整个实体，在这些框架里是怎么声明和生成的？有没有「一个字段声明它对谁可见」的成熟形态？
- **共用的边界事故**：有没有公开记述的、因为前后端共用导致的真实事故（把服务器数据同步给了不该看的客户端、两端版本不一致、客户端反编译拿到服务器逻辑）？
- 与之相对：**坚决不共用**的框架是怎么做的、为什么这么选。

#### C. World / Scene / 实体命名空间

- `World` 这个容器在各框架里的形态：一个进程几个 World、World 之间能不能互相引用、跨 World 查询是否被禁止。
- 服务器权威 World 与客户端投影 World 的对应关系：是「同一实体在两个 World 里各有一份」还是别的模型？身份映射怎么维护？
- **`Scene` 与 `World` 的关系**：画像里有 `OnEnterScene` / `OnLeaveScene`，但「Scene」在不同引擎里语义差别巨大（关卡？空间分区？可见性集合？AOI 范围？）。**把工业界对「Scene」这个词的几种用法列清楚，并指出画像用的是哪一种、这个命名有没有歧义风险。**
- 实体命名空间的隔离与回收：World 销毁时旧句柄怎么失效、是否允许跨 World 句柄泄漏。

#### D. 实体的声明、原型与创建路径

- **「先声明实体类型、创建时绑定一组组件」这种机制**在各框架里的对应物：原型 / 蓝图 / Prefab / 实体描述符 / 定义文件 / 必需组件（required components）/ 继承与组合关系。逐个说清**声明发生在编译期还是运行期**、能不能热更。
- 实体类型的**继承与变体**：能不能「在 A 类型基础上加两个组件得到 B 类型」？各框架的做法与限制。
- **创建路径的性能构成**：分配、组件初始化、注册到查询索引、生命周期钩子调用、结构提交，各占多少。
- **海量创建的优化手段全清单**：对象池、批量创建 API、原型缓存、预留容量、延迟提交合并、写时复制、免分配路径。
- **实测数字**：谁公开过「每秒创建 N 个实体」「N 万实体稳定运行」的数据？引用出处与测试条件。**没有数据就标 `Estimated` 并写清推断依据，绝对不要编数字。**
- 销毁路径的对称问题：延迟销毁、墓碑、引用失效、销毁期间的重入。

#### E. Component 模型（画像的核心特征之二）

- **组件带逻辑时，组件之间怎么协作**？把工业界的几种做法列全并对比：直接持有引用、通过实体查询、事件 / 消息、依赖注入、System 中转。各自的耦合度、可测试性、可确定性代价。
- **组件依赖与顺序**：必需组件 / 互斥组件 / 依赖声明能不能表达？初始化顺序由什么决定？「A 组件的 Awake 里访问 B 组件」这个经典问题各家怎么解。
- **跨组件引用的失效**：B 组件被移除后 A 手里的引用怎么办？有没有句柄化 / 弱引用 / 代际校验的成熟做法？
- 组件的增删时机：运行时能不能加组件、加组件是不是结构变更、结构变更为什么几乎都要延迟。
- **`Transform` 专节（重点，画像称它为最核心的组件）**：
  - 为什么几乎所有引擎的 Transform 都是特殊组件：父子层级、局部 / 世界变换、脏标记与传播、层级重排的代价。
  - 在 ECS 里表达层级的几种方案（父引用、子列表、层级深度排序、关系型 ECS 的原生关系）及其对并行与确定性的影响。
  - Transform 的**网络表示**：同步的是局部还是世界？量化与压缩到什么精度？插值 / 外推放在哪一层？
  - Transform 与物理、渲染、AOI、空间索引的耦合点清单——**这些耦合点决定它能不能被当作一个普通组件对待**。
- **`Model` / 表现组件专节**：逻辑与表现的边界怎么画。**这一条与「前后端共用」直接冲突——服务器根本没有模型**。工业界怎么处理这种「组件只在一端存在」的情况？（条件编译？空实现？端侧组件集？表现层完全外置？）逐个列出并给出各自的代价。
- **能力即组件**：「挂一个能力组件，实体就获得一整套能力」这种做法的先例与边界。能力组件与普通组件在生命周期、同步、存储上有什么不同待遇？（**能力系统内部机制见 GAS 专项，此处只看组合接口面**。）

#### F. 生命周期语义（**重点章**）

- **生命周期钩子全表**：把主流引擎与框架的实体 / 组件生命周期钩子列成一张对照表，逐个注明触发时机、能不能在钩子里创建 / 销毁实体、失败了会怎样。至少覆盖：主流商业引擎的组件生命周期、几个主流开源 ECS 的 hook / observer 机制、几个主流网络框架的两端生命周期回调。
- **`Awake` 与 `Start` 为什么要分成两个**——找到设计者的原话或权威解释，把背后那个具体的坑挖出来（提示：与「所有组件都建好之后才能互相引用」有关，但请核实并给出出处）。**如果分成两个还不够，工业界有没有分成三个四个的？**
- **`OnEnable` / `OnDisable` 的语义**：什么叫「禁用」？被禁用的实体还 Tick 吗？还占存储吗？还同步吗？还能被查询到吗？各框架的答案与不一致之处。
- **AOI 驱动的 Enter / Leave 事件**：把「进出可见范围」做成生命周期回调的先例逐个列出（提示方向：老牌网络引擎的 scope in / scope out、商业引擎的 relevancy 与 dormancy、开源网络框架的 observer / interest 回调、MMO 引擎的进出视野回调）。每个说清：**事件在哪端触发、携带什么数据、进入时是否推全量、离开时对象是销毁还是隐藏还是保留。**
- **关键判断题（必须给出明确结论）**：
  - 把 **AOI 进出**和**启用 / 禁用**做成两套独立语义，还是合并成一套？工业界的主流选择是什么，理由是什么？
  - **服务器 AOI 与客户端 AOI 是同一个概念吗**？如果不是，用同一对钩子表达会产生哪些歧义？举出具体会出错的场景。
  - 画像里 `OnEnterScene` 在 `Start` 之后、`OnDisable` 在 `OnLeaveScene` 之后——这个**线性顺序**成立吗？现实中这些事件会不会乱序、重入、或在一帧内成对发生（进了又出）？各框架怎么防。
- **生命周期与延迟提交的对齐**：结构变更延迟到提交点，那 `Awake` 到底在提交点之前还是之后触发？在钩子里再创建实体会怎样（递归提交？下一帧？直接报错？）——**这是画像第 8 号硬问题，重点挖。**
- 生命周期钩子的**失败语义**：钩子里抛异常怎么办？半初始化的实体怎么收场？在 fail-stop 帧模型下这意味着什么。
- 生命周期与**存档 / 快照恢复**的关系：从快照恢复出来的实体，六个钩子跑不跑？跑哪几个？

#### G. 属性同步（**最高优先级重章之一**）

这一章要写到能让人照着重新实现的程度。

- **「声明即同步」的实现形态全景**：把工业界的做法分类列全——属性标记 / 特性（attribute）、独立定义文件（IDL / DSL / def）、Schema 声明 + 代码生成、显式注册表、手写打包。每一类给出：**声明写在哪、代码怎么生成、运行期靠反射还是生成代码、AOT 与裁剪友好度、可 diff 与可 review 性。**
- **脏标记粒度**：整实体 / 整组件 / 字段位掩码 / 子字段 / 容器增量。位掩码方案的字段数上限与扩展方式。粒度对带宽和 CPU 的实际影响。
- **变更检测方式**：写入即标脏（setter 拦截）、帧末 diff 对比、版本号 / Revision 比对、写屏障。各自的代价与对「组件带逻辑」模型的适配度。
- **通知时机（重点）**：属性变化回调是**逐字段立即回调**还是**批量提交后统一回调**？两种做法各自的经典 bug（半更新状态下被回调看到、回调里再改属性、回调顺序不确定）。**画像有唯一提交点，这一条直接相关。**
- **同步的调度**：频率、优先级、带宽预算、按距离降频、可靠 / 不可靠通道的分工、打包与合批。
- **可见性与权限**：全体可见 / 仅 owner / 仅队友 / 服务器私有，怎么声明、怎么裁剪、裁剪发生在哪一层。**没做裁剪会暴露什么作弊面**——找具体案例。
- **初始状态与增量**：进入视野时的 Baseline 全量、之后的 Delta、晚加入者补齐、重连补齐。Baseline 的构造成本与压缩。
- **数值属性（Attribute）的同步**（与普通字段的区别）：
  - 服务器算完同步**结果值** vs 同步**输入 / 事件**让客户端自己算——两条路线的取舍（带宽、一致性、预测友好度、作弊面）。
  - 「基础值 / 当前值」二分在同步上的表现：同步哪一个？为什么？（**修饰器求值属于 GAS 专项，此处只看同步面。**）
  - 属性变化与其它状态（如效果、Buff）到达顺序不一致时的经典问题。
- **与预测的耦合**：被预测的字段和权威字段能不能混在同一个组件里？权威值到达时怎么覆盖本地预测值？
- **失败模式清单**：丢包、乱序、重连、AOI 抖动导致的重复 Baseline、字段增删导致的版本不兼容、同步风暴。
- **一句话总结**：这一派的同步哲学是**同步状态**还是**同步事件**？在哪些地方各选了哪一种、为什么。

#### H. AOI / 兴趣管理（**最高优先级重章之二**）

- **学术根**：分布式虚拟环境里的兴趣管理研究（提示方向：分布式仿真标准里的数据分发管理、aura / nimbus 之类的兴趣模型、以及兴趣管理综述类论文）。**给标题、作者、年份**；查不到全文就标注只读到摘要。
- **工程实现全清单**：网格 / 九宫格、十字链表、四叉树 / 八叉树、KD 树、可见性预计算、基于查询的订阅、基于距离的相关性判定。每种给出：更新复杂度、实体规模适配区间、抖动特性、实现难度。
- **进出 AOI 的事件语义**：进入时发什么（全量？增量？分帧推送？）、离开时客户端怎么处理（销毁？隐藏？留墓碑？留多久？）、**同一实体反复进出**时的行为。
- **抖动抑制（重点）**：滞后带 / 双阈值、延迟销毁、软离开、优先级队列、分帧摊销。有没有公开的参数经验值？

- **AOI 与生命周期绑定的正反证据**：找出明确这么做的框架和明确不这么做的框架，各自给出理由。**这一条直接决定画像里 `OnEnterScene` / `OnLeaveScene` 的设计成不成立。**

#### I. System / 执行模型与帧结构

- 在「组件带逻辑」的模型里，System 还剩什么职责？工业界的几种分工方式。
- **更新顺序**：显式排序、依赖声明、分组 / 分相、优先级数字。乱序会出什么问题，各家怎么防。
- **并行**：读写集声明、冲突检测、结构变更与并行的天然冲突。「组件带逻辑」的模型能并行到什么程度（诚实评估）。
- **帧内分相与提交点**：有哪些框架也采用「一帧一个结构提交点」？延迟命令缓冲的设计（命令去重、冲突、稳定合并顺序、同帧创建又销毁）。
- **事件与消息**：帧内事件 vs 跨帧事件、事件的存储与回收、事件顺序的确定性、事件风暴的抑制。

#### J. 性能与规模（画像明确要求「创建快、性能好」）

- **「组件带逻辑」模型的性能天花板由什么决定**：缓存局部性、虚调用 / 接口分发、指针追逐、GC 压力、装箱、闭包分配。逐条给机制解释，不要只说「慢」。
- **托管运行时（C#）下的实测**：主流 C# ECS 框架的公开 benchmark 对比（创建 / 查询 / 迭代 / 增删组件）。**引用出处与测试条件**；benchmark 之间口径不一致的地方要点出来。
- **Storage 表示对性能的实际影响**（直接服务画像的未决选型）：Archetype / 列存 vs Sparse Set vs 混合，在**创建速度、增删组件速度、查询迭代速度、内存占用、结构变更成本**这五个维度上的公开数据与定性结论。**明确指出「海量快速创建 + 频繁增删组件」这个负载画像更偏向哪一种。**
- GC 与分配策略：免分配路径、值类型组件、内存池、原生内存、跨托管 / 原生边界的代价。
- **真实量级**：多少实体 × 多少组件 × 多少 Hz 是被公开验证过的？服务器端 N 个玩家 + M 个 AI 的经验数据。**引用出处；没有就标 `Estimated`。**
- 性能测量方法本身的坑：微基准与真实负载的差距、只测迭代不测结构变更的常见误导。

#### K. 客户端预测与权威收敛（与 G 章耦合）

- 与画像的「整帧作为单一确认 / 回滚单元」对比：有没有框架也是整帧粒度？没有的话，字段级 / 实体级粒度的代价是什么。
- 预测失败的用户可见后果与标准规避手法。

#### L. 确定性、快照与版本演进

- ECS 状态能否被稳定序列化与哈希：迭代顺序、字典 / 哈希表顺序、浮点累加顺序、实体创建顺序、组件注册顺序——哪些是稳定性杀手，各框架怎么处理（或回避）。
