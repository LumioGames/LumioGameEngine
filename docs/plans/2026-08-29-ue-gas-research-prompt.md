### 1. 我们到底想从 GAS 学到什么

不是要一份「GAS 入门介绍」。委托方正在自研一套 Gameplay Ability 框架，想从 UE 这套跑了十年、扛住过 Fortnite 规模的实现里学四样东西：

1. **学它的进取心** —— Epic 当初为什么要造这么重的一套东西？它试图一次性解决哪些历史顽疾（技能、buff/debuff、资源消耗、冷却、免疫、堆叠、状态标记、表现层、网络同步全都塞进一个系统）？它的野心边界在哪里，哪些野心落地了，哪些至今没落地（Epic 自己都要在 Lyra 里额外补一层）？
2. **学它的设计逻辑** —— 每一个抽象为什么存在。为什么要把 Attribute 拆成 BaseValue/CurrentValue？为什么要有 Meta Attribute 这种"中转属性"？为什么 Tag 是计数而不是布尔？为什么 Effect 要区分 Instant/Duration/Infinite？**每个设计的背后都有一个具体的坑，把那个坑挖出来**——这比记住 API 名有价值一百倍。
3. **学它在各方面的实际应用** —— 同一套 GAS 在 ARPG、FPS、MOBA、生存建造、MMO、单机项目里分别被怎么用、怎么裁剪、怎么被绕过。Lyra / ActionRPG / Fortnite 的真实用法差异。
4. **学它的精髓，尤其是这两块（本次调研的最高优先级）：**
   - **数据同步**：GAS 到底把什么复制过网络、怎么复制、复制多少、怎么省带宽、失败时怎么办。
   - **状态回滚与收敛（reconciliation）**：客户端预测了一个技能，服务器不认，接下来到底发生了什么。是回滚重放，还是覆盖收敛？边界在哪？代价是什么？

最终这份报告要能回答一个问题：**这套东西的哪些设计是可以被一个技术栈完全不同的引擎继承的「思想」，哪些只是 UE 特定实现的「包袱」。**

### 3. 目标环境画像（用于判断可迁移性，自包含，不需要查任何代码）

委托方的引擎与 UE 差异很大，做可迁移性判断时以这张画像为准：

| 维度 | 目标引擎的形态 |
|---|---|
| 语言与运行时 | Rust 原生内核 + C# 托管层跑 Gameplay；**没有 UObject、没有引擎级 GC 对象图、没有蓝图虚拟机、没有 Actor 复制模型** |
| 状态存储 | **ECS 是被复制的 Gameplay 状态的唯一权威存储**；Ability 框架自身只保留索引和瞬态执行上下文，不做第二份状态真相 |
| 帧模型 | 逻辑 Tick 分相推进，一帧内有**唯一的提交点**；提交点之前的写入对复制/快照不可见，提交点之后重复执行必须幂等 |
| 故障模型 | Tick 内故障是 **fail-stop**：不做字段级撤销，整帧作废，从快照 + 日志重建 |
| 权威模型 | 服务器校验并提交；客户端只能在**有界的预测窗口**内预测；Ability 状态、ECS 状态、世界体素覆盖层属于**同一个确认/回滚单元**，要么一起确认要么一起回滚 |
| 确定性诉求 | 需要可复现的求值顺序与**可计算的状态哈希**，用于回放、对账与崩溃恢复 |
| 分层 | 框架层拥有通用的 Ability/Effect/Attribute/Tag 生命周期、句柄、时间与快照；内容层只拥有具体类型、公式、消耗、冷却、目标选择和表现事件 |
| 已冻结的生命周期语义 | Ability 实例状态固定为：`Requested → Activated → Executing → Completed`，另有 `Rejected`（激活被拒）、`Cancelled`（任一非终态可进）、`Expired`（执行中超时）、`RolledBack`（预测被权威拒绝）；终态使句柄失效。Effect 实例状态固定为：`Pending → Active → Expired | Removed`，另有 `Rejected` 与 `RolledBack`；**堆叠、持续时间刷新都是 `Active` 内的事件，不是独立状态** |
| 已知待解的硬问题 | ① 类型 ID / 实例 ID / 句柄的三层区分 ② 堆叠、持续时间、取消三者的先后顺序 ③ Modifier 的求值顺序 ④ 预测键机制 ⑤ 确认 / 拒绝 / 回滚窗口的边界 ⑥ Ability 状态与 ECS 状态的单一真相 ⑦ 快照与状态哈希的投影方式 |
| 明确推迟的能力 | 高级触发图（Trigger Graph）、公式虚拟机（Formula VM）、复杂依赖求解器 |

**注意**：以上只是判断迁移性的参照系。**不要去评审这套设计的对错，也不要建议改它**——你的产出是"UE 是怎么做的 + 这个做法能不能在上述形态下成立 + 代价是什么"。

#### A. 起源、野心与设计哲学

- GAS 的历史来源：从 UE3/Gears/Paragon/Fortnite 一路演进的痕迹，能查到多少写多少。
- 官方对它的定位原话（找到并引用），以及 `GameplayAbilities` 插件在当前版本的成熟度措辞（是否仍标 Experimental/Beta——这一点很多人说不清，请核准并给出证据）。
- **它试图一次性解决的问题清单**：技能激活、资源消耗、冷却、持续效果、堆叠、免疫、状态标记、条件互斥、表现层解耦、网络同步、设计师可配置……逐条列出，并说明每条在没有 GAS 的年代是怎么用一次性代码解决的。
- **通用化的代价**：为了覆盖所有品类，它付出了哪些抽象层数上的代价？哪些概念是"为了少数场景存在、却让所有人都要理解"的？
- **哪些野心没落地**：Epic 自己在 Lyra 里额外补了一层（Ability Set、全局 Ability 系统、初始化流程封装等）——这些补丁精确指出了裸 GAS 的缺省能力缺口，**逐个列出并解释缺口性质**。
- 一句话概括它的设计世界观（然后用证据支撑这句话）。

#### B. 整体架构与对象图

- 核心类型与依赖方向：能力系统组件（ASC）、Ability、Effect、Effect Spec、Effect Context、AttributeSet、Tag、Cue、AbilityTask、各类 Handle。画出对象图（文字或 mermaid 均可）。
- 谁持有 ASC：挂在 Pawn 还是 PlayerState？两种选择的动机、后果（复活、复制模式、跨关卡持久化）与社区共识。
- Owner Actor 与 Avatar Actor 分离的动机与实际后果。
- **耦合点清单（对本次调研极其重要）**：GAS 与 UObject/GC、Actor 复制、蓝图 VM、动画 Montage、Timer/World Time、资产系统（DataTable/CurveTable）、输入系统的每一处耦合，逐条写明"耦合在哪个类的哪个能力上"。**这张清单直接构成后面的「不可照搬清单」。**
- 数据流总览：一次技能从输入到表现的完整链路（含网络往返）。

#### C. 标识、句柄与实例模型

- 各类 Handle（Ability Spec Handle、Active Effect Handle、Effect Context Handle、Prediction Key 等）的：生成方式、唯一性范围（进程内 / 连接内 / 全局）、生命周期、失效时机、能否跨端比较、能否序列化进存档。
- 句柄复用与 ABA 问题：UE 防了没有？怎么防的？
- 是否存在"类型 ID / 实例 ID / 句柄"的三层区分？如果没有明确三层，实际是几层，缺的那层带来了什么问题？
- Ability 的实例化策略（非实例化 / 每 Actor 一实例 / 每次执行一实例）：状态存在哪、性能差异、可预测性差异、各自的禁忌。这是新手最常踩的坑之一，挖细。

#### D. Ability 生命周期

- 完整调用链，从"能否激活"检查到结束/取消的每一步，以及**每一步的失败出口**分别产生什么后果。
- 提交（Commit）语义：为什么消耗和冷却要在一个独立的"提交"步骤，而不是激活时就扣？这个设计解决了什么问题？（这条与预测强相关）
- 网络执行策略的几种取值（仅本地 / 本地预测 / 仅服务器 / 服务器发起）各自的实际网络流，以及安全策略选项。
- Ability 之间的互斥、阻塞与取消：依靠哪些 Tag 字段（拥有的、需要的、阻塞的、取消的），**它们的求值顺序**，以及"已授予但当前被阻塞"这种状态在系统里是怎么表示的。
- 触发方式：输入绑定、Gameplay Event、Effect 授予、被动 Ability 的自动激活。
- **产出一张 Ability 状态对照表**：把 UE 实际存在的状态位（含隐式状态）与第 3 节列出的目标状态名（`Requested/Activated/Executing/Completed/Rejected/Cancelled/Expired/RolledBack`）逐个映射。重点回答：UE 里"已授予但被 Tag 阻塞"、"等待目标数据"、"等待动画结束"这些中间态分别落在哪？目标模型只允许在 `Executing` 内定义业务子状态，这够不够用？

#### E. GameplayEffect：数值系统的核心

- 持续策略（瞬时 / 有限时长 / 无限）与周期性执行；周期的时间基准、漂移与对齐问题。
- Modifier 的运算类型（加 / 乘 / 除 / 覆盖）与数值来源（可缩放浮点 + 曲线表、基于属性、由调用方设置、自定义计算类）。
- 自定义执行计算与属性捕获规则：**捕获时机（快照 vs 非快照）× 捕获对象（来源 vs 目标）** 这个二维矩阵的四种组合各自什么语义、什么场景用——**这直接决定数值可复现性，重点挖**。
- **Modifier 求值顺序**（重点）：基础值 → 各聚合通道 → 当前值的确切顺序；覆盖类 Modifier 如何抢占；同优先级如何定序；结果是否依赖 Effect 的应用顺序或容器迭代顺序；**同一组 Effect 以不同顺序应用，最终数值是否相同**（回答这个问题需要证据）。
- **堆叠**（重点）：按来源聚合 vs 按目标聚合、堆叠上限、刷新时长策略、周期重置策略、到期策略、溢出 Effect、堆叠被拒时的返回值。**堆叠、时长刷新、取消三者同时发生时的先后顺序**是什么？
- 移除与免疫：按 Tag 移除、免疫 Tag/查询、被免疫时应用方拿到什么结果。
- Effect 授予 Ability、授予 Tag、以及**持续 Tag 条件（Ongoing Requirement）导致的"抑制态"**：Effect 还在但被抑制不生效——这个状态在目标模型的六个 Effect 状态里没有对应物，**请精确描述它的语义、进入/退出条件、以及在网络与快照中的表现**。
- Meta Attribute（伤害/治疗中转属性）模式：为什么需要它，不用它会怎样。
- Effect Spec 与 Effect Context 携带的信息：来源、发起者、命中结果、随机种子（如有）等，以及它们在网络上的传递成本。

#### F. Attribute 系统

- 基础值 / 当前值二分的动机、聚合器（Aggregator）的重算时机与触发源。
- AttributeSet 的注册、初始化（含从表初始化）、访问器宏做了什么。
- 钳制（Clamp）应该写在哪个钩子里：几个可选钩子各自能钳什么、钳错了会出什么 bug（这是社区高频坑）。
- 属性变化的通知链路：变化事件、RepNotify、与 UI 的绑定方式。
- **迁移性分析**：属性存在 UObject 字段里 vs 存在 ECS Component 里——聚合器重算模型还成不成立？需要改什么？

#### G. GameplayTag 系统

- Tag 的内部表示、层级匹配语义（精确匹配 vs 含子级匹配）、Tag 查询表达式的能力边界。
- Tag 的注册来源（配置文件 / 数据表 / 原生声明）与"Tag 表"的构建时机。
- **Tag 的网络序列化**：如何压缩（索引化）、客户端与服务器的 Tag 表必须多一致、表不一致会怎样、热更新/版本升级时的兼容风险。**这条对任何有 Release/版本哈希模型的引擎都有直接启发，重点挖。**
- Tag Count 语义：为什么是计数而不是布尔？松散 Tag（Loose Tag）与复制 Tag 的区别与各自适用场景。
- 性能特征：容器匹配与查询的代价、常见滥用模式（把 Tag 当字符串用、Tag 爆炸）。

#### H. 数据同步 / 网络复制（**最高优先级重章之一**）

这一章要写到能让人照着重新实现的程度。

- **复制全景图**：ASC 上到底有哪些状态要过网络？逐类说明——属性、激活中的 Effect、已授予的 Ability、Tag 计数、Cue、目标数据、预测键。每类的复制方向（服务器→客户端 / 客户端→服务器）、复制粒度、可靠性等级。
- **复制模式**（完全 / 混合 / 最小 三种）：确切差异、各自把什么发给谁（自己 vs 其他客户端 vs 仿真代理）、适用场景、带宽差异量级、以及"混合模式对 ASC 挂载位置的隐含要求"这个著名陷阱。
- **增量数组复制**：激活中的 Effect 容器用的快速数组序列化机制——增量粒度是什么（整项 vs 字段）、增删改分别怎么传、接收端的回调时机、乱序与丢包时的行为。
- **属性复制的细节**：复制的是基础值还是当前值？为什么？客户端如何重建当前值？属性与 Effect 到达顺序不一致时会出什么问题（这是有名的坑，找证据）。
- **Ability 的复制**：已授予 Ability 列表怎么复制、实例化的 Ability 对象是否复制、输入状态是否复制。
- **上行方向**：客户端到服务器传什么——激活请求、目标数据、预测键、输入确认。服务器对这些上行数据的**校验点在哪**（防作弊边界）。
- **RPC 批处理**：把"激活 + 目标数据 + 结束"打包成一次 RPC 的机制，解决什么问题、省了多少、有什么限制。
- **带宽优化手段全清单**：最小复制模式 + Cue 的组合、只给 owner 的数据、相关性（relevancy）剔除、Tag 索引压缩、不复制的本地推导量。
- **与引擎通用复制系统的关系**：GAS 建立在 Actor 复制之上的哪些假设；UE5 新一代复制系统（Iris）出现后 GAS 的现状与迁移情况——**核实清楚，不要猜**。
- **时间同步**：服务器世界时间的复制、客户端如何算冷却剩余、时钟偏移与延迟补偿的处理。
- **失败模式清单**：丢包、乱序、重连、相关性变化导致的状态缺失、Cue 丢失、客户端晚加入（late join）时如何补齐已有的持续效果。
- 一句话总结：**GAS 的同步哲学是什么？**（是"同步状态"还是"同步事件"？还是混合？在哪些地方选了哪一种、为什么。）

#### I. 客户端预测与状态回滚 / 收敛（**最高优先级重章之二**）

这一章是本次调研的核心诉求，要挖到底。

- **设计意图**：为什么 GAS 要自带一套预测，而不复用引擎里角色移动组件那套成熟的回滚重放机制？两者的问题域差异是什么？
- **预测键机制全貌**：键怎么生成（客户端递增？）、怎么随激活请求上行、服务器如何确认或拒绝、依赖键（一个预测动作派生出另一个）的链式关系、键的生命周期与作用域窗口。
- **"预测应用"到底做了什么**：客户端在本地立即应用了哪些东西（Effect？Tag？Cue？动画？属性？冷却？消耗？），服务器权威结果到达后如何收敛。
- **撤销机制**：预测被拒绝时，具体撤销了什么、靠什么数据结构撤销、哪些东西**撤不掉**（已经播出去的表现、已经触发的连锁）。
- **本章必须给出明确结论的关键判断题**：
  - GAS 的机制究竟是 **① 回滚 + 确定性重放（resimulate）**，还是 **② 乐观应用 + 权威覆盖收敛（reconciliation）**？给出确凿证据。
  - 如果是 ②，那么"回滚"这个词在 GAS 语境下的准确含义是什么？与目标引擎要求的"预测帧内回滚、整帧作为一个确认单元"相比，差在哪、差多远？
  - GAS 有没有"预测窗口"这个概念的等价物？窗口边界由什么界定（时间？帧？RPC 往返？）
- **官方明确的"不预测清单"**：哪些东西官方文档直说不预测（找到原文）。为什么不预测——是做不到还是不值得？
- **预测失败的用户可见后果**：属性弹回、Cue 播了又撤、动画打断、冷却抖动。社区有哪些标准规避手法。
- **消耗与冷却的预测**：客户端本地怎么扣、服务器怎么收敛、双方不一致时谁赢。
- **横向对比**：与角色移动组件的回滚重放、与网络物理/Chaos 的回滚、与引擎的新一代网络预测插件（Network Prediction Plugin）各自的模型差异与现状。**这个对比是本章价值最高的部分**——因为目标引擎要的是"整帧作为单一确认/回滚单元"，而这三者代表了三种不同的答案。
- **规模与适用边界**：这套乐观收敛机制在什么延迟、什么玩家规模、什么品类下成立？什么时候会明显崩掉（高延迟？强对抗？复杂连锁技能？）
- **精髓提炼**：用几段话说清这套机制的核心取舍——它拿什么换了什么，以及一个要求确定性与状态哈希的引擎能不能接受这笔交易。

#### J. GameplayCue：表现层解耦

- Cue 的类型（静态 / Actor 型）与事件种类（执行一次 / 添加 / 持续期间 / 移除）。
- Cue 的网络路径与**可靠性等级**：会不会丢？丢了会怎样？为什么这样设计（带宽 vs 表现完整性的取舍）。
- Cue 与逻辑的分离靠什么强制——是类型系统强制，还是只靠团队约定？违反了会怎样？
- 客户端晚加入时，已经在生效的持续 Effect 的表现怎么补。
- 对"框架层不含表现、内容层提供表现事件"这一分工的启发：**Cue 把边界画在哪，值不值得抄，抄的时候要注意什么。**

#### K. AbilityTask 与异步执行

### 7. 交回物格式

交付时在会话里按五段回复（**附件 + 正文，缺一不可**）：

1. **产出**：上传的 zip 文件名与大小、包内文件清单、报告规模（章节数、字数量级）。
2. **执行摘要全文**：直接贴在正文里，**不要让委托方为了看结论去解压。**
3. **调研证据**：实际用到的信息源清单（分类计数）+ **信息源可达性的实际情况**——哪些打开了、哪些打不开、哪些块是源码级证据、哪些只是文档级。**不要只写「已完成」。**
4. **Known gaps**：没查到或查不准的问题，逐条说明卡在哪、建议下一轮怎么查。
5. **最重要的三个发现**：三句话，给决策者看。其中至少一句必须是关于**数据同步或状态回滚**的判断。

### 8. 检索线索与执行建议

**GitHub 在线检索的实操要点（省时间，照做）：**

- 先用**符号名**搜，不要用自然语言：搜 `UAbilitySystemComponent`、`FGameplayEffectSpec`、`FPredictionKey`、`FActiveGameplayEffectsContainer`、`FGameplayTagContainer` 这类具体标识符，命中率远高于搜「ability」。
- 用 `path:` 限定缩小范围。**先用 tree 视图确认 GAS 与 GameplayTags 模块的实际路径**（不同版本目录会挪位），再进 blob 视图读——**不要凭记忆写路径。**
- 引用时点开文件后**选中行号再复制链接**，拿到带 commit hash 的 permalink——分支链接会随时间失效。
- 官方样例工程（Lyra 一类）如果在这个仓库里，它是「Epic 自己认为的当代最佳实践」，**含金量高于任何社区文章**；先在 tree 视图里确认它在不在、在哪。
- GitHub 代码搜索有速率限制，**批量搜索前先规划关键字清单**，不要一个词一个词地试。

- **起点**：Epic 官方文档站的 Gameplay Ability System 章节；引擎源码中 `GameplayAbilities` 插件目录；官方 Lyra 示例工程及其文档；官方 ActionRPG 示例。社区侧公认最全的是 GASDocumentation 这类长文仓库——**极有价值，但务必标注为社区来源并核对版本**。以上均为待核实的检索线索，**若与实际不符以实际为准，并在报告里纠正本提示词的说法**。
- 章节之间基本独立，**可以按章节分组并行推进**，但 H 与 I 两章建议由同一条线索连续做完（它们高度耦合）。并行产出合并成一份报告时，**不得丢失置信度标注与来源**。
- 遇到"我记得好像是这样但查不到"的时刻，**停下来标 `Estimated` 或写进 Known gaps**。这份报告会被用来做架构决策——一个诚实的空白远比一个自信的错误有价值。
- 如果在调研中发现了本提示词没问到、但对"数据同步 / 状态回滚 / 可迁移性"很关键的东西，**主动加一章写进去**，并在执行摘要里点出来。
