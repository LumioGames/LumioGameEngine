# 配表常驻内存估算模型

## 固定工作负载假设

- 行数为 `N`，每行 20 列。
- 8 列为 4-byte 的 `i32/u32/enum/ref`；4 列为 8-byte 的 `i64/u64/f64`；4 列为 `bool/低基数小枚举`；4 列为字符串。
- 每个字符串平均 12 个 ASCII 字符；字符串值总体 50% 重复。托管字符串按 UTF-16 估算；紧凑/零拷贝方案按共享 UTF-8 池估算。
- 只有主键索引；没有二级索引、反向引用图、调试 provenance、业务派生缓存。
- 目标是**数量级和相对差异**，不是承诺值。对象头、字段布局、引用宽度和 GC 行为在 CoreCLR、.NET WebAssembly 与 Unity IL2CPP 之间不同，最终必须在目标发布构建上测量。[S094–S097]

## 公式解释

### 通用对象 + 装箱

一个 `object[20]` 行容器约含数组头和 20 个 8-byte 引用；16 个非字符串标量若装箱，每个又产生一个对象。再加字符串对象、顶层行引用和索引，估算为 `700–1100 B/行`。若使用 `Dictionary<string, object>` 并在每行重复保存 key/bucket/entry，这个区间会明显上移。

### 强类型托管行对象

假设一个行对象持有内联标量和 4 个字符串引用。字符串仍是独立对象；即使值池化，行对象、引用数组与哈希索引仍有固定开销。估算为 `230–360 B/行`。

### 结构体数组 + UTF-8 字符串池

标量连续放入结构体数组；字符串字段仅保存 `offset/length`，重复值在池中共享。主键用排序 `(id,rowOrdinal)` 数组或紧凑 hash。估算为 `128–160 B/行`。

### 零拷贝列/混合 view

数值列连续存储，布尔与 presence 位图化，字符串列用 offset array + UTF-8 data buffer。按当前假设约 `123–132 B/行`。这个方案省的是对象与复制，不等于没有内存：索引、字符串池、缓存与解压缓冲仍然存在。

## 峰值而非常驻值

激活期间应单独测：

`Peak = Active驻留chunk + Staged新增chunk + 压缩输入 + 解压输出 + 校验工作区 + 索引 + 旧代尚未释放chunk`

对不可变内容寻址 chunk，Active/Staged 未变化部分可以共享；变化 chunk 与解压缓冲仍会叠加。浏览器内存失败通常由峰值触发，而不是稳态常驻值。
