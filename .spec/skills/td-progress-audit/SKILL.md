# TD · Progress Audit(引擎总监 · 定期进度盘点与对账)

把「各仓做到哪了、Workflow 说做到哪了、两者差在哪、接下来怎么排」变成一次可重复执行的盘点。产出物固定三件:**本地评估报告**、**Workflow 对账写入**、**每仓开工派活提示词**。首次成型于 2026-08-28 盘点(报告样例:`docs/reviews/2026-08-28-seven-repo-progress-assessment.md`;派活样例:`docs/plans/2026-08-28-kickoff-dispatch-prompts.md`)。

跨仓派活与核验的机制细节以 [`cross-repo-delivery`](../cross-repo-delivery/SKILL.md) 为准,Workflow API 口径以 workflow 插件技能为准;本技能只定义盘点流程本身,不复述。

## 真值分层(盘点的第一原则)

| 问题 | 唯一真值 | 不是真值的东西 |
|------|----------|----------------|
| 需求要做什么、做到哪个状态 | Workflow 需求单(lumiogamesengine) | 本地快照文档、记忆、口头声称 |
| 公共契约长什么样 | 架构仓 Baseline/Schema/ID/Fixture | 各仓镜像(只是副本) |
| 代码实际做没做 | **已推送 origin 的提交** | 任何机器的本地工作区、未推送分支 |
| 测试过没过 | **链接执行的真实输出** | cargo check / type-check / 「已通过」声称 |

开发横跨多台机器(Windows `C:/Work/LumioGames` 与 macOS `~/LumioGames`)时,origin 是唯一可信汇合点。

## 盘点流程(五步)

### 1 · 仓库侧事实采集

- 所有仓 `git pull --ff-only`;记录各仓 HEAD、脏文件、未推送/异常分支。
- 每仓量化:源码/测试文件数与行数、模块覆盖(几个模块有实现)、本仓任务机制状态(`.spec/tasks/` 等)、evidence/审查文档结论。
- 并行手段:互不重叠的仓可用 Explore 子代理扇出调研。

### 2 · Workflow 全量核对(只读)

- 验证连接(`/me`、`/projects/current` 三方一致)后拉全量:所有 Room、全部需求卡(cursor 取全量,空 `nextCursor` 才是终点)、里程碑与归属。
- 汇总每 Room 状态分布;对关键卡按四路读全(正文+评论+附件+验收项)——**改口、裁决、差异记录都在评论里**。

### 3 · 双向漂移对账(核心步骤)

对每个 Room 回答两个方向:

- **仓库领先**(交付在 origin、卡还停在早期状态)→ 补证据评论 + 按项目工作流流转到与事实一致的状态;验收未实跑的**最多流转到「实现中」**,不越级。
- **Workflow 领先**(卡状态靠前、origin 上找不到交付)→ 逐卡核验证据:`git ls-remote` 确认提交在 origin,`git show --stat` 确认提交内容**覆盖改动清单**。不可复核的卡补差异记录评论(不改状态),写明解铃条件(如「Windows 侧推送后重核」);在重核通过前不得向「已完成」流转。

授权边界:既有卡的流转/评论在 cross-repo-delivery 持续授权内;**新建卡/Room/里程碑必须逐次取得用户明确授权**(确切对象清单+数量),内容认可不等于写入授权。

### 4 · 本地评估报告(必须落仓内文件)

报告写入架构仓 `docs/reviews/YYYY-MM-DD-*.md` 并提交——**不以链接/网页作为交付形式**(用户明确要求)。固定章节:

1. 执行摘要(完成度总览表 + 核心结论 ≤3 条)
2. 各仓详情(每条结论附出处:文件路径/提交号/卡号)
3. Workflow 现状(Room × 状态分布表)
4. 漂移对照与证据核验结果(含不可复核清单与解铃条件)
5. 关键路径与下一阶段 wave 编排(W0 解阻类必须「不完成不进下一 wave」)
6. 风险与开放决策(含建议裁决方向)
7. 本次已执行动作 / 待授权事项

### 5 · 派活(每仓一份开工提示词)

- 落地 `docs/plans/YYYY-MM-DD-kickoff-dispatch-prompts.md`,每仓一份可直接粘贴的提示词。
- 提示词只做三件事:**指路**(哪些卡、什么顺序、环境注意事项)、**立规**(公共纪律)、**设禁区**(不许碰什么);工作内容本体永远在 Workflow 卡上,提示词不复述卡面。
- 派活边界:同仓串行、异仓并行;解阻类(W0)先派;有守门条件的仓(如等上游推送)提示词第一步就是守门检查,不满足即停并回报,不得绕过重做。

## 公共纪律(嵌入每份派活提示词)

① 领卡先流转「实现中」(reason 写明);② 证据评论只引用已推送 origin 的提交号,先 push 再回写;③ 测试证据必须是链接执行的真实输出;④ 交付 = 改动清单 + 验证证据 + known gaps + 沉淀落点,本仓收口门槛必过;⑤ 公共契约缺口 → 停,卡上标 BLOCKED 上报,不本地绕过;⑥ 只动本仓文件;⑦ 做完流转「验收中」,「已完成」由总调度核验后流转。

## 正确性与效率的平衡手段

- **效率**:文件集互斥即并行(跨仓天然互斥;SPIKE/设计卡可与实现卡并行);解阻卡优先级永远高于新功能卡;状态欠账按模块批量补,不逐卡人工考古。
- **正确性**:写的人 ≠ 审的人(reviewer 闭环);验收流转必须有实跑证据;工具链 pin 落卡前双机实测可解析;`cargo check` 不当测试证据;每次盘点把复发问题沉淀进 `knowledge/lessons.md`。

## 验证

- 报告每条结论有出处,无裸声称;未执行的验证标「未执行」。
- 每笔 Workflow 写入读回核验(状态/评论数/归属)。
- 架构仓收口门槛通过后才提交报告与提示词。
