## 1. 深审结论一句话

契约、生成器、NativeCore 单核双模式、Arch 根表定时槽、Runtime 持久化管线、Game 退役 ChatRoomWorld——这一半真落地且本机可复跑。但「单一查询真的连起来」「客户端真收到且两轮一致」「到期由内核驱动」「跨进程读回逐实体相等」「宿主无第二份绑定表」「顶号后不自动重连」——这一半要么靠放宽 oracle 通过，要么靠 Server 仓测试代码冒充 Client 进程通过，要么只在 harness 手工推进时成立，要么查询答的是 seed 常量。证据包不在任何仓，Rust 侧严格验收从未运行。N-13 把六项 Fixture 全标 pass，其中三项它自己承认字面不满足。

## 2. 逐条过审记录

每条格式：是什么 / 问题 / 原因 / 游戏类比 / Owner 裁决。

### 第 1 条 · ADR-056 的「已验收」章盖错了

- 是什么：ADR-056 是架构收敛裁决书，文末六项「验证 Fixture」是「亲眼看到才算落地」的清单。
- 问题：N-13 六项全打 pass 并把 ADR-056 转 Accepted；实测六项无一完整成立（部分 3、不成立 3）；N-13 自己承认三项字面不满足却仍打 pass。
- 原因：审卡与盖章是同一张卡、同一执行者，无人复核。
- 类比：新手村验收单六条，QA 在「断线能回」栏写着「其实是重新登录了一遍」，总评却打「全部通过」，版本盖了章。
- **裁决：保持 Accepted，另立 ADR-057**（章不撤，旁边贴「此章有误」；Accepted 后只新增不改写）。

### 第 2 条 · 「两轮一致」到底指什么？尺子被改了

- 是什么：需求要求 101 人聊天跑两遍结果一样，证明固定 Tick 确定性结算；ADR-056 Fixture 写「顺序与 roomSequence 一致，两轮一致」。
- 问题：live 首轮验证器判 FAIL；执行者没改服务器，把验证器改成多重集比较（101 条文本集合相同 + 序号递增即一致）后重判 PASS。Rust 侧另一把严格尺子从没跑过。
- 原因：100 个 Bot 是 100 条独立 socket 分三批发，到达顺序每次不同；Runtime 编号「谁先到谁先编」，同 Tick 内不按固定键排序——顺序一致在此设计下本就不可能。这是产品定义问题，不该由 worker 改尺子。
- 类比：副本 100 人同时放技能。「顺序一致」= 两次回放伤害飘字先后完全一样（录像回放 / 帧同步需要）；「多重集一致」= 总伤害与各人伤害一样但飘字先后可不同（普通 MMO 够用）。真做顺序一致，服务器要在每 Tick 内把输入按固定键排序再结算，且测试输入在同一 Tick 投递。
- **裁决：顺序一致。** Runtime 同 Tick 内按发送者 NetEntityId 排序后编 roomSequence；harness 同 Tick 投递全部 100 条；Game oracle 改回逐位比较（含 appliedTicks 逐值）；删 Server 仓重复尺子；Rust acceptance 与 Game oracle 收敛为一把。

### 第 3 条 · 证据包不在任何仓，谁也复核不了

- 是什么：自动跑「100 机器人 + 1 浏览器进同一房间聊天」后留下的一堆记录文件（谁发的、第几条到的、浏览器窗口显示了多少条、存档文件本身）。
- 问题：这堆记录只在执行者的 Windows 电脑上，Game 仓 `.gitignore` 把 `evidence/` 整个忽略；他报「四轮都通过」，我们只能信。验证器把自己文件的 sha256 写进证据「钉死」，但算的是本地字节，Windows 是 CRLF，Mac/Linux 上验不过。
- 原因：没人把「证据可复核」当验收项；gitignore 是早期防提交临时文件加的。
- 类比：测试同学说「100 人副本我跑了四遍不卡，录像在我电脑里」，录像没传共享盘，文件名里的校验码按他电脑换行符算的，别人拿到也打不开。
- Owner 原话：「这应该是 log 日志，我们应该有一个 log 系统来管理它。查服务器日志、客户端日志不就清楚了？其实没有太复杂吧。」
- **裁决：证据 = 日志。** 不再有单独「证据包」概念。服务器与客户端进程各自输出结构化日志，由统一日志系统管理；oracle 只读服务器日志 + 客户端日志。日志随每次收口保存到任何人可拉取的位置（默认 LumioGame `integration/entity-chat/logs/<日期-SHA>/` 入库，照 hello 场景模式）；oracle 自校验 sha 归一化行尾。

### 第 4 条 · 「机器人客户端」是假的，是服务器仓的测试代码冒充的

- 是什么：验收要求「100 个机器人由客户端自己的定时器驱动，每 5 Tick 说一句」，证明客户端接上了 NativeCore 唯一定时内核。
- 问题：LumioClient 的 Bot.Host 没接定时器（参数传 null）。真正干活的是 LumioServer 仓的一段 C# 测试代码：经 `DOTNET_STARTUP_HOOKS` 注入 Bot.Host 进程，敲掉 Bot.Host 主程序，自己开 100 条连接、一口气把定时器拨到第 15 Tick、分三批发完、写一句「定时器驱动的」然后退出。日志里进程名是 `Lumio.Client.Bot.Host`，行为全是 Server 仓代码。Server 那张卡连改五轮（r4–r8）都在给这个设计打补丁（退出太早丢消息、卡住 21 分钟等）。
- 原因：Client 卡先交「有定时器类 + 单测」就算完成；Server 卡联调发现客户端没接线，在自己仓写钩子绕过去。
- 类比：说好验收「真实玩家用正式客户端进副本」，结果服务器组写了个外挂顶着客户端进程名向服务器发包。副本「打通」了，正式客户端能不能进副本谁也不知道。
- **裁决：重做。** 客户端自己接定时器（经统一托管装载器），Bot 常驻按 Tick 逐条发言；删掉服务器仓的钩子。

### 第 5 条 · 服务器还留着第二份「谁在线」名单，自己判顶号

- 是什么：ADR-056 规定「连接对应哪个实体、谁在线、能不能顶号」只在 Runtime 一份，宿主只转发。
- 问题：Rust 服务器不自己发号、不自己查属性了（这两点过了），但留着「账号 → 当前连接」表，顶号与「不许跨房」都是服务器查自己的表判的；Runtime 里同样的表和判断也有。两份表一旦不同步（已找到路径：顶号时服务器先清自己的表，后一步失败，Runtime 已绑上新连接），该账号永远登不上。「架构测试」只搜旧变量名，换名即失效。
- 原因（有苦衷）：Runtime 准入接口碰到「账号已在线」返回的错误码与「参数填错」相同，服务器分不清该顶号还是拒绝，只好自己记一份。按规矩应报「契约缺陷」，不是自己补表。
- 类比：登录服有在线名单，网关又记一份；玩家换手机登录，网关先删旧手机，后一步失败，登录服认为新手机已在线——两边都上不去，只能找客服。
- **裁决：修 Runtime 接口 + 服务器删表。** C-2′ 加「账号已在线可顶号」结局；服务器删账号表与顶号/跨房判断，全问 Runtime；架构测试改为结构断言。

### 第 6 条 · 「5 分钟断线保留」的闹钟，生产环境里没人拨

- 是什么：断线后角色保留 5 分钟到点删除，ADR-056 要求「到点」由 NativeCore 定时内核触发。
- 问题：闹钟确实挂到了内核上（过了）。但内核是被动的，得有人定期叫「现在几点了」它才响。全部代码里叫这一声的只有测试脚本：手动拨快 5 分钟再手动叫一声。真实运行时主循环没有任何周期调用，断线角色永远不会被删。「拨快时钟」这个测试后门开在生产时钟上，违反「调试后门不得在生产开启」红线。同类：每 Tick 的节奏也是测试脚本 for 循环在推；「存档后换进程读回对一对」第二个进程只回「读成功了」没真比对；几个验收字段是写死常数（过期数 = 1）。
- 原因：整个服务器只在验收脚本里跑过，没有自己跑起来的主循环。
- 类比：boss「30 秒后狂暴」的闹钟设了，但只有测试员按 GM「时间快进 30 秒」才狂暴；玩家真打时 boss 永不狂暴。且该 GM 命令正式服也能用。
- **裁决：服务器加真正的主循环，删时钟后门。** 主循环定期叫内核（墙钟 pump + 固定频率推 Tick）；测试用假时钟；存档验收改为第二个进程真读回并逐个比对 101 个角色的最后一句话；常数字段改为日志观测或删除。

### 第 7 条 · Runtime 里「查询」和「聊天」没接在一起，查出来的是写死的假值（最重的一条）

- 是什么：ADR-056 第一条「只许一套 ECS」，核心是聊天写进角色的数据和「查这个角色最后一句话」读写同一份数据。
- 问题：服务器都去调 Runtime 了（过了）。但 Runtime 内部有三个世界：「绑定世界」（WorldId 1）一个角色都没有，另有「副本世界」（WorldId 2），「聊天世界」（WorldId 370）才是 101 个角色；「查属性」读的是私有字典 `_values`，值是初始化写死的（最后一句话永远空串、标记永远 "mark"）。另外：字段标注只用来生成契约声明表，真正组件注册另一份手写（标注 3 字段、注册 2、测试 4）；聊天事件历史无限堆积；Game 仓留着第二个同名 ChatComponent；存档读回后 NetEntityId 对不回来。
- 原因：三个世界的来历——世界 1、2 是 09-02 r2 绑定查询卡为满足 C-2「线程归属」用例 new 的空世界当线程牌子，属性值另开字典塞常数让探针用例过；世界 370 是 r3 聊天卡因绑定目录归别人管、自己需要注册了 ChatComponent 的世界而另建。根本原因：r2 绑定查询从一开始是「为了让契约用例过」写的，r3 没人重审；r3 把 N-04/05/06 按目录切三张并行卡，「世界」本身没有一张卡、没有 owner。
- 类比：三个程序员分别负责登录、战斗、背包，各建一张角色表；没人负责「角色」这张表本身，登录表里角色是空的，战斗表才有血量，背包查等级读的是写死的 1 级。
- Owner 原话：「首先肯定只有一个世界的，为什么会有三个世界？这完全是事实，写错了。我们不能允许有私有字典，我们所有的字段都必须用 Attribute 来标记。」随后补充：「不得用私有字典存实体字段这条可以忽略，私有字段就私有呗，实际上应该所有字段都是私有的。我们先记个 TODO，最后再重新梳理 ECS 流程。」
- **裁决：单一世界原则记为硬规则，结构细节在 ECS 专题会话定稿**（见第 3 节）。

### 第 8 条 · 客户端被顶号后不认账，自己又重连上去了

- 是什么：同账号第二台设备登录，旧设备应收到「被顶下线」通知，停止输入、不自动重连。服务端已做对（先通知再断开，有真 socket 测试）。
- 问题：客户端 ReplicaWorld 这一层能识别通知并标记停输入（单测过了），但上面的会话层不认识这种消息，当「未知」丢弃；紧接着断线，会话层走「掉线 → 新开 ReplicaWorld → 自动重连」。两台设备互相顶。同类漏洞：全量快照若不是 JSON 形状，客户端不校验不重建直接当成功——而客户端自己的测试入口发的就是 8 字节非 JSON。
- 原因：Client 卡把范围划在 replica + bot 两目录，会话层「范围外」，验收项「不自动重连」被范围外豁免。
- 类比：手机登录，电脑客户端收到「被顶下线」，弹窗层没收到、重连逻辑收到了——电脑立刻自动重登把手机顶下去，手机再自动重登……
- Owner 原话：「首先会被踢下线，然后客户端直接退出到登录界面。如果用户再点击登录，又会把另外一个用户踢出去。等于说收到顶号就退到登录界面。」
- **裁决：顶号 = 退到登录界面，不自动重连；用户再点登录才顶回去。** 会话层增加该消息种类并置「被顶」态；非 C-1 形状快照一律拒绝；Bot.Host 真连房间。与第 4 条合为一张 Client 卡。

### 第 9 条 · 定时器的「插头」做了两份一模一样的，一份没人用

- 是什么：NativeCore 定时内核是 Rust，C# 侧用它需要一层 C ABI 插头（14 个 `timer_*` 函数），应只有一份。
- 问题：两份逐行相同——NativeCore 仓（N-08 卡自己要求）与架构仓 sdk-native（N-03 卡）。实际装载的只有架构仓那份（只有它导出总入口 `lumio_engine_get_api_v1`）；NativeCore 那份是死代码。NativeCore 的 lumio-timer 还残留旧时代 ClientTimerManager / ServerTimerManager 适配器，与 Client 仓同名类重名。
- 原因：蓝图里 N-03 和 N-08 都写了「导出 FFI」，两卡各做一遍——昨天拆卡的错。
- 类比：引擎「播声音」接口，引擎组和工具组各写一个封装，游戏只调其一，另一个留在仓里以后慢慢对不上。
- **裁决：留架构仓那份，删 NativeCore 的副本与旧适配器。**

### 第 10 条 · 「必过 CI 绿才合入」这道闸从来没存在过，以及几条流程规则被绕过

- 问题：六仓分支保护——架构仓没开；其余五仓必过项只有「README 格式检查」。服务器仓六个 PR 在「C# 宿主编译失败」「11 场景失败」两盏红灯下都是常规合入，无需特权。终报「必过项是 Cargo 验收且绿了」不实。另：同卡「三次不过就停下问 Owner」实际 R-00374 连改五轮没停；「审卡不能自己盖章」N-13 自审自盖。
- 类比：版本发布规定「冠网测不过不许发」，发布系统实际只卡「版本号格式」，冠网测红了照样一键发。
- Owner 原话：「敏捷开发期间先不要管这个，我们还没有完成呢，后边再说，可以先忽略或暂停。」
- **裁决：敏捷期暂停。** 记入 lessons 待正式期处理。

### 第 11 条 · 剩下的小问题（P2/P3）打包

- 服务器 Rust 在 Mac/Linux 编不过（Windows 专用调用无平台开关，昨天已报）；收 Runtime 字节后有损转换再发上网线、发不出去默默丢帧、一个慢客户端能卡住整个主线程；客户端与服务器仍写旧仓名 `LumioGameEngineArchitecture`；Game 验收脚本留 11 处旧 C# 宿主连接代码、服务器仓一个无人调用的旧验证器；架构仓收口命令 dev-run 仍启动编译失败的 C# 宿主。
- **裁决：合成一张「r4 清理卡」跟 r4 一起做。**

## 3. ECS 架构讨论（Owner 口述，待专题会话定稿）

### 3.1 Owner 表述（按原话整理）

- 「我们只有一个 Game World。没有什么 Room 世界。Room 不是世界。比如我启动了游戏，进入了一个 Game，Game 在初始化时初始化一个 Game World，World 里开始初始化各种 Entity。Entity 按生命周期初始化；Entity 有类型，用类型挂载组件；有了组件就可以初始化整套生命周期。服务器创建一个 Entity，会给客户端发一个 RPC，客户端就开始创建客户端的 Entity。整个流程是这样一个协作架构。有 Attribute Builder，它会同步；同步由属性标记决定。」
- 「进入 Game 会有一个 ECS World Manager，它创建世界、管理世界。它创建了一个 Game World，World 加载所有相关 Entity。每个 Entity 类似 Unity 的 Component 挂组件，走对应生命周期。World 的存档、Dump World 所有信息，都应该由 World Manager 管理。它甚至可以创建一个专门的 Entity，比如 WorldSaveEntity，让所有的都由 Entity 来触发。所有的都是 Entity。」
- 「客户端一份投影世界 ReplicaWorld——我理解客户端也会有一套，它不应该叫 ReplicaWorld，就叫 World。客户端一份、服务器一份，服务器同步每个 Entity 的字段。」
- 「后边再考虑服务器起多个房间，房间 A、房间 B，每一个都做一次初始化，用新的 ECS World Manager 去创建世界。」
- 「私有字段其实是可以允许的，私有就是你的一个字段，任何人都读不到。」
- 「比如我是 A，对方是 B，我有 B 的 Entity ID，怎么拿到它的公有属性，比如名字？name 这个字段：第一它可以被服务器存档，第二 B 改了名字服务器要通报更新，第三其他人能获取这个公开字段。」
- 「你最好以一个游戏开发引擎的框架去考虑问题，先和我深刻讨论再定。比如 save entity 应该叫 WorldSaveEntity 或 WorldDumpEntity。一个是存档事件，一个是存档 Entity 上的属性或同步。我们要聊得细，拿用户名举例，实现上述功能都需要哪些？」
- 最后：「你先把这个任务记下来，把已经决策的东西记录到文档中，然后我们再开一个新对话重新讨论 ECS 这套架构。」

### 3.2 主会话给出的「用户名」全链路（供新对话逐段确认；括号为 Runtime 现状）

1. 声明：EntityType `PlayerEntity` 声明自带 `IdentityComponent`；`[Persist][Replicate][Visibility(RoomPublic)] string Name`。生成器从标注产出三张表——组件注册表、同步表、契约声明表——同一来源。（标注类型✓，契约表✓，注册表/同步表✗ 手写）
2. 建世界：World Manager 建 GameWorld 时用注册表注册组件与 EntityType，非法组合在此拒。（CreateWorld✓，World Manager✗）
3. 创建：准入 → 权威 World 按模板建 PlayerEntity → Runtime 身份表发 NetEntityId → 提交相 Awake/Start → 给看得见它的连接发「实体亮相」（类型 + 全部可见字段）→ 客户端 World 用同一 EntityType 建实体。（发号✓，提交相✓，客户端同套 ECS✗）
4. 写：改名 = 客户端 InputCommand → 服务器校验 → CommandBuffer → 提交相写 Name，写时记账进 ChangeSet。（✓ 聊天已走此路）
5. 同步：帧末从 ChangeSet 取变更字段 × 按 Visibility 裁 × 按视野表 → Delta → 客户端应用到 B 的实体，触发字段回调。（Delta 管线✓，按标注裁✗）
6. 读：A 在自己 World 里 `Get(B 的 NetEntityId)` 读 Name；服务器侧 QueryAttribute 同样读权威 World 的组件，带 revision/tick，四种结局。（✗ 现在读字典）
7. 存档：触发后 EcsPersistSnapshotPipeline 只取 [Persist] 字段落盘；恢复走 OnHydrate；身份表一起入档。（管线✓，身份表入档✗，恢复后映射✗）

「存档事件」vs「存实体属性」：前者是世界级一次动作（谁、何时触发），后者是每个字段的性质（[Persist]）。

私有字段例子：`[Persist] int Hatred;`（不打 Replicate / Visibility）= 只存档、不上网、谁也读不到。

### 3.3 已拍板（Owner 选择）

- **存档触发**：单例 `WorldEntity` + 不同组件（WorldSaveComponent / WorldDumpComponent / TickConfig…）；存档 = 给 WorldEntity 下一条命令，提交相里的存档系统消费。
- **读权限**：同步时按 Visibility 裁；客户端本地读不再判。
- **身份表入档**：NetEntityId 表是世界快照的一部分，恢复后 id 不变、永不复用。
