# ADR-036: Voxel Streaming Durability Acknowledgment, Residency Modes and the Eviction Fence

- **Status**: Accepted (additive to Implementation Baseline `LGE-V1.3-2026-08-27`, accepted 2026-08-27; ships with the next BaselineId cut by the owner)
- **Owner**: `LumioVoxelEngine` (world/streaming state), Host/`LumioGameRuntime` (persistence orchestration and acknowledgment issuer)
- **Baseline**: `LGE-V1.3-2026-08-27` line
- **Relation**: Completes the write-side durability loop opened by [ADR-024](ADR-024-voxel-p0-contract-set.md) (`applyDurabilityAck` port method, `Dirty`/`Evicting` chunk states) and [ADR-025](ADR-025-voxel-participant-receipt-durability.md) (receipts co-durable with world state). Consumes the snapshot durability points of [ADR-035](ADR-035-voxel-snapshot-payload.md) and the WAL record identity of [ADR-032](ADR-032-durable-recovery-records.md); supersedes none of them.

## Context

The voxel chunk model defines `Dirty` as "committed authoritative changes not yet recorded by any snapshot or WAL", yet the streaming state machine allowed `Dirty -> Evicting -> Unloaded` with no durability fence: nothing defined who acknowledges durability, what an acknowledgment identifies, or where a chunk stops when the host fails, the disk is full or the receipt is lost (voxel review VXL-010, contract gap §7). Streaming and snapshot modules explicitly do not own file durability, so an unfenced eviction can permanently destroy acknowledged voxel writes or resurrect stale pages. The commit protocol frozen elsewhere already requires that dirty state is published atomically with revisions at the barrier and that only a host durability receipt may clear it; the receipt shape itself was never frozen.

## Decision

- **`DurabilityAck` record.** The host's persistence orchestration acknowledges durability to a voxel world through one record naming: the world and its `{contextId, generation}` context, an `ackId`, the covered chunk set as an array of `{chunkId, upToChunkRevision}` pairs in the ADR-035 canonical chunk order, a `coveredWorldRevision`, and a `durabilityPoint` that is a snapshot reference (`snapshotId`), a WAL position (`walSegmentId` + `walOffset`), or both — exactly one of the three shapes, discriminated structurally. The world applies acknowledgments only at its barrier through the `applyDurabilityAck` port entry; a chunk's dirty marker clears only for revisions `<= upToChunkRevision`. Later writes leave the chunk `Dirty` for the remainder. Re-applying an acknowledgment is idempotent; an acknowledgment for a destroyed context is rejected by generation, exactly like every late completion.
- **Unloading a Dirty chunk requires protection.** A `Dirty` chunk may leave residency only after (a) a durability acknowledgment covers its current chunk revision, or (b) the world explicitly runs a volatile residency mode (below). An eviction attempt on an unprotected dirty chunk fails with the new stable error `DirtyChunkNotDurable` (1038) and the chunk stays resident; nothing may silently drop dirty pages, downgrade them to `Unloaded`, or flush them from streaming code that does not own durability.
- **Eviction fence record.** Every eviction decision on a `Ready` or `Dirty` chunk is expressible as an auditable `EvictionFence` record: chunk identity and state, the world's residency mode, and the decision. An `Evict` decision on a `Dirty` chunk must name exactly one protection path — the covering acknowledgment (`coveringAckId` + `coveredUpToChunkRevision`) or the explicit volatile capability — never neither, never both. `Deny` is always legal and is the default outcome; a deny caused by missing coverage carries `DirtyChunkNotDurable` as its reason.
- **Residency modes and capability hookup.** A world runs exactly one immutable `ResidencyPolicy`, declared at creation from host configuration: `AllResident` (unload disabled entirely — the P0 all-resident profile; requires the `VoxelAllResident` capability, numeric 8), `DurableEviction` (the default: eviction only behind acknowledgment coverage; no extra capability), or `VolatileAllowed` (declared loss boundary for lightweight hosts; requires `VoxelVolatileChunks`, numeric 9). The capabilities ride the existing `host-capability` `capabilities` list and the ADR-024 world-port capability set — no envelope field changes. Under `AllResident`, every eviction decision is structurally `Deny`.
- **Dedicated-server default.** On `Online` room-mode hosts, an Authority world defaults to `DurableEviction` and must not run `VolatileAllowed`: a dedicated server never evicts a dirty chunk that no recovery guarantee covers. `VolatileAllowed` is legitimate only where the host manifest explicitly declares the loss boundary (e.g. singleplayer light-durability profiles), and even then the fence record must witness the capability per eviction.
- **Receipt alignment.** Because ADR-025 makes participant receipts co-durable with world state, a durability point that covers a chunk's writes also covers the receipts recorded with them; acknowledgment-driven eviction therefore never separates a transaction's writes from its receipt.

## Contract

`schemas/voxel-durability-ack.schema.json` (`kind` = `DurabilityAck` | `ResidencyPolicy` | `EvictionFence`), registered in `schemas/index.json` as P1 `VoxelEngine`; new registry entries `DirtyChunkNotDurable` (ErrorCode 1038), `VoxelAllResident` (Capability 8) and `VoxelVolatileChunks` (Capability 9) in `ids/index.json`. `snapshot-header` and `host-capability` schemas are unchanged; the hookup is by capability id only.

## Failure semantics

An acknowledgment without a durability point, or naming neither a snapshot nor a WAL position, is malformed. An `Evict` fence on a dirty chunk with no protection path — or with both paths at once — is malformed. An `AllResident` world emitting any `Evict` decision is malformed. Rejected evictions return `DirtyChunkNotDurable` and keep the chunk resident with its dirty pages intact; host failure, disk pressure or a lost acknowledgment leaves the chunk `Dirty` (or `EvictionRequested`) indefinitely rather than unloading it. Clearing dirty state without an acknowledgment, or losing acknowledged coverage while keeping the writes, is a fatal world fault, not a retryable error.

## Alternatives

TTL/LRU eviction of dirty chunks was rejected: silent loss of committed authoritative writes. Making streaming flush pages before eviction was rejected: streaming does not own snapshot/WAL durability and a second flush path would fork the persistence orchestration. A boolean "durable" flag per chunk was rejected: revision-precise coverage (`upToChunkRevision`) is required once writes pipeline past an in-flight snapshot. A volatile mode declared only by capability bit, without a per-eviction fence witness, was rejected: audit and failure bundles need the decision record. Registering a combined "resident+volatile" capability was rejected in favor of two orthogonal declarations.

## Compatibility and migration

Additive to the `LGE-V1.3-2026-08-27` line; chunk states, the port method set and existing capability numerics are unchanged, and no deployed streaming consumer exists yet, so no migration window is required. Changing the acknowledgment shape, the fence protection rules, residency mode names or the default eviction policy later requires a new ADR, new fixtures and a new BaselineId.

## Verification

Fixtures `voxeldur/ack-snapshot-point` (snapshot durability point covering a chunk set), `voxeldur/ack-wal-point` (WAL durability point), `voxeldur/residency-all-resident` (all-resident declaration with its capability), `voxeldur/fence-dirty-covered-evict` (dirty eviction behind acknowledged coverage), `voxeldur/fence-dirty-uncovered-deny` (default deny for unprotected dirty chunks), `voxeldur/fence-dirty-uncovered-evict` (unacknowledged dirty chunks must not unload), `voxeldur/ack-missing-durability-point` (acknowledgment must carry a durability point), `voxeldur/fence-all-resident-evict` (all-resident mode disables eviction). Implementations must additionally inject host-crash, disk-full and lost-acknowledgment faults and assert that no dirty chunk unloads and no acknowledged write is lost.
