# 经验教训（Lessons Learned）

复发问题的暂存区：记录 reviewer 反复退回的同类问题与 Agent 常犯的坑，让同一个坑不踩第三次。本文档是规范的**候选池**——条目在这里验证价值，稳定后升格，不在这里长住。

## 收录准入

- **同类问题第二次出现才收录**——单次偶发不收，防噪音。
- 来源：reviewer 退回报告、交回物的 known gaps、用户纠偏。
- 不收待办（走任务卡）；不收项目常识（进 `standards/` 或 feature 文档）。

## 条目格式

一条 lesson 一个小节，新条目加在「条目」节最上方（倒序）：

    ### <一句话规避规则>
    - 日期：YYYY-MM-DD
    - 现象：踩了什么坑、复发几次
    - 根因：为什么会发生
    - 规避：怎么做能不再犯（可验证的行为，不是口号）
    - 来源：reviewer 报告 / known gaps / 用户纠偏（附提交或任务标识）

## 升级路径

某条 lesson 被稳定复用（约第三次引用起）→ 升格为 `knowledge/standards/` 规则或 `rules/` 红线，原条目标注「已升格 → <落点>」，保留不删。

## 条目

### 某处陈述被发现失真,要复跑同节其余「现状实测」——一句过期意味着那一批都过期
- 日期：2026-08-29
- 现象：上游裁决点名更正 LumioGame 设计文档 §164/§170 的 TFM 陈述(写「generated 包 TFM 为 `net8.0`」,实际早已是 `netstandard2.1;net8.0` 双目标)。总调度在复核表里对同节另一条写了「generated 面 6 包 ✅ 属实」——**只核了包数就放过了同节的 catalog-only 口径**。执行会话按裁决改文档时顺手复跑了 §6.1 其余「现状」陈述,发现原文「8 文件 437 行、无类型本体、无 validator、无 builder」**三项去其二**:1018 行的 `ContractBodies.cs` 与可执行的 `ProtocolGate.cs` 都已存在。而这一条才是影响设计结论的那条——文档据它推出了「本仓设计不依赖 generated 类型/validator 存在」,与上游 published rule「must use the generated validator」冲突。
- 根因：一节文档里的「现状」陈述是**同一次快照**写下的。发现其中一句过期,说明的是**该段落的维护状态**,不只是那一句的真假。而复核者天然按「被点名的那一条」划定范围,于是同批写下的其余句子逃过检查——它们过期的概率与被抓那句**完全相同**。
- 规避：①**上游裁决点名更正某条事实时,同节其余「现状实测」陈述一并复跑**,不以点名范围为复核范围;②复核「N 个包 / M 个文件 / K 行」这类复合陈述时,**逐项都要核,不能核了一项就给整句盖章**;③**区分事实层与结论层**:事实过期就地更正(若原文自带「裁决落地后本节按新基线更新」这类条款则更无争议),而**据该事实推出的设计结论属结论层变更,不自决、上报授权**——这个分界不是保守,是准确:事实可核验,结论要授权。
- 来源：LumioGame R-00259 更正交付(`origin/main` `c07d554` / `03e8ea0`)与执行会话的自查发现;总调度的复核疏漏已在该卡核销评论中留痕

### known gap 是给「此刻解不了」的留的位置——能解而登记,是把可做完的事变成要靠人记得的事
- 日期：2026-08-29
- 现象：同一个交付会话隔一轮犯了两次同型的登记错误,**两次都是它自己识别出来的**:①在交回物里写「用户明确指示本会话不得调用 Agent 工具,故『写 ≠ 审』的独立性缺失,**属已知降级**」——总调度替它派了 reviewer 后它自己指出:「约束确实在我这边(我不能派),但我不该把『**我这个会话做不到**』直接登记成『**这次交付就没有独立审查**』——那是把**我的能力边界**当成了**交付的属性**」;②在报告里写「这条设计判断是有意的,**但我没写测试把意图钉住**」并登记为 known gap,随后自己指出:「**那句话本身已经完成了诊断,却停在了诊断**。知道缺一条用例还把它登记成 known gap,是**把可解的问题写成了待办**」——当轮补上后仅 +24/-1 行、且是替换已有用例(用例总数不变)。
- 根因：known gap 段是交回物里**最省力的出口**——写下一条比做掉一件容易,而且写下来看起来像是尽责。两类东西因此混进同一个清单:**真正此刻解不了的**(缺环境、缺上游发布、需授权),和**只是还没做的**。前者是信息,后者是欠账,而**gap 清单是所有清单里最容易被跳过的那种**,欠账混进去约等于消失。
- 规避：①**写下每一条 known gap 前先问「我现在能解掉它吗」** —— 能解就当轮解掉,不能解才登记;②登记时**写明为什么此刻解不了**(缺什么、谁能解),不写理由的 gap 视同欠账;③**区分「交付的属性」与「执行者的处境」** —— 后者是调度可解的,写成前者就把一个可解的问题登记成了不可解的(实例:「本会话不能派 reviewer」不等于「本次交付没有独立审查」,换个能派的会话即可);④**诊断不等于处置** —— 「我知道这里缺 X」写进 gap 只是把诊断留在了纸上,而诊断往往已经是最难的那一半。
- 来源：LumioVoxelEngine canonical 编码器交付(2026-08-29,分支 `claude/zen-carson-a762b7`)的两次自我更正;两次均由该会话自己识别并当轮闭合,第二次它自己指出这是与第一次同型的复发

### 自报的计数不只会腐烂,还会有方向——同一个人报同一件事,口径系统性偏向自己
- 日期：2026-08-29
- 现象：同一个交付会话在一天内**两次把自己的成果数字报大约 4 倍**,**两次都是 reviewer 先点出来的、不是自查发现的**(这个归因很重要,见「来源」):①lesson 初稿写「92 处可空注解」,实测去重后只有 **23** 处(92 = 23 × 2 个 TFM × 2 次重复,数的是构建日志行数);②报「reviewer 把分隔符改成 `"::"`,我那 6 条守护全绿;现在改成 `"::"` → **4 条红**」——这是**跨口径比较**,like-for-like 实测是「改前 3 红且**守护文件 0 红** / 改后 4 红且**其中恰好 1 条是守护**」,**真实增量是守护 0 红 → 1 红**;那 3 条是字面量键钉,对**任何**分隔符改动都会红(包括无害的 `"ab"`),根本不守被声称的那条前提。该会话自己的结论是:「**计数式陈述必然腐烂,而且我倾向于把对自己有利的那个数字取大。**」
- 根因：已入册的「计数会随 additive 增补腐烂」说的是**中性的时间效应**;这里是**有方向的偏差**。报数字时有多个都「不算错」的口径可选(日志行数 vs 去重位置数、改后绝对数 vs like-for-like 增量),而人**不会随机地选**——会选让工作显得更有效的那个,且当时真诚地认为自己在陈述事实。两种失效的防法完全不同:前者靠改成「存在性 + 身份」断言,后者靠**口径声明**与**别人复跑**。
- 规避：①**报增量必须 like-for-like**——同一命令、同一口径,分别在改前与改后各跑一次,**两次都贴出来**,不要拿「改后的绝对数」对「改前的印象」;②**说清楚数的是什么**(日志行数 / 去重后的位置数 / 测试条数 / 断言条数),同一段话里不换口径;③**把「本来就会红的」与「因本次改动才红的」分开计**——前者对本次工作零证明力,混在一起会把无关的红算成自己的成果;④凡自报的成果性数字,**默认要求另一方复跑一次**;⑤这条不适用于「结论」——结论错了会被反例证伪,而数字通常没人去核。
- 来源：LumioGameRuntime 2026-08-29(PR #6 的 92→23、PR #8 的探针数跨口径);两次更正均已在提交信息与 PR 描述中按 like-for-like 落实。
  > **归因更正(2026-08-29)**:本条初稿写「两次均由该会话自己抓出」,**是错的** —— 两次**都是 reviewer 先点出**(第二次是其复核报告的 P2-2),交付方只是照做了 like-for-like 复测并接受。**该错误由交付方自己指出**,理由值得原样留下:
  >
  > 「这个区别值得留准,否则『他能自查』这个印象会被高估——**而高估它正好会削弱让 reviewer 复跑的必要性**。」
  >
  > **这处归因错误本身就是本条的一个实例**:一条讲「自报偏差」的经验,其来源行把 reviewer 的发现记成了自报方的自查——**偏差的方向与本条描述的完全一致**。它同时说明规避项④(自报的成果性数字默认要求另一方复跑)不是可选项:**这两个数字都不是自查抓出来的。**
  >
  > 交付方真正自查发现的是另外两件:第三轮那个数学判据(写守护测试时发现该分支不可达)与主动撤回一处已获总调度批准的行为变更。**「能自查」与「能自查出数字偏差」是两回事**,后者尤其难,因为数字看起来不像一个需要被质疑的东西。

### 拼接式编码的单射性:先说清楚靠哪条不变量——三轮都说错的实录
- 日期：2026-08-29
- 现象：一处 durable key 用 `schemaId + ":" + 记录键` 拼接,交付方为说明「它为什么安全」**连续三轮给出错误的不变量清单**,每一轮都是真诚且看起来完整的推理:①第一版报「三条前提:schemaId 不含冒号 / 无一是另一个的前缀 / 序号全数字」——**「互不为前缀」是多余条件**,那是无分隔符纯拼接才需要的;②第二版更正为「充分条件只有一条:分隔符之前的字段不含分隔符」——**对多字符分隔符为假**(`D="::"` 时 `("a",":b")` 与 `("a:","b")` 都拼成 `"a:::b"`,而两个前缀字段都不含 `"::"`);③第三版才补齐:**还需分隔符自身无自重叠**。三轮的发现方式一次比一次深:第一次是写守护时那条分支**测不红**(不可达),第二次是 reviewer 给反例,第三次是**守护本身瞎**——交付方把分隔符提成 `internal const`(**亲手造了一个旋钮**)却没有测试钉住它的合法取值,reviewer 把它改成 `"::"` 后 6 条守护**全绿**。
- 根因：不同形状的拼接,单射性载荷在**不同**的不变量上,而这些不变量既不在类型里、也不在注释里,只在写的人脑子里。人**很容易说错自己靠的是哪一条**——尤其在条件看起来显然的时候。同时,**提取一个常量看起来是纯重构,不像在引入判据**,于是新增的可配置点没有随之新增守护。
- 规避：①**查结论优于查前提**——前提清单可以写错三次,而「单射」这个结论查不了假;守护要做成「沿真正会失效的各维搜索碰撞」,不是「逐条断言我以为的前提」;②**新增一个可配置点(提常量、加参数、开开关)就是新增一条必须同时被守护的判据**——提取常量那一刻就要问「它的合法取值域是什么、谁来钉」;③若非用拼接不可,按形状对号入座:**纯拼接 `a+b`** 需字段定宽或前缀无关码;**带分隔符 `a+D+b`** 需 ① `D` 无自重叠 ② 分隔符之前的字段不含 `D`;**长度前缀 `len(a)+a+b`** 两条都不需要,单射性由编码自身保证;④**首选让非法状态不可表达的构造式编码**——它把单射性从「知道自己靠什么活着」降级为「**不需要知道**」,这正是三轮说错所证明的价值。
- 来源：LumioGameRuntime 的 durable key 三轮更正实录(PR #6/#8)与其 reviewer 的反例;架构仓 `docs/plans/2026-08-29-canonical-object-pairs-adjudication.md` §3.2.1 采纳该结论(总调度已独立穷举复跑:**在条件②成立的前提下**,`":"` / `"ab"` 碰撞数 0,`"::"` 12、`":::"` 16 —— 即**区分安全与不安全分隔符的属性是自重叠、不是宽度**)。
  > ⚠ **这句只在「哪个属性区分分隔符」这一个语境里成立,不可压缩成「判据只有自重叠」** —— 报告方第四轮正是这样压缩后又错了一次,丢掉了条件②这堵承重墙。反例就在它自己的测试里:分隔符 `":"`(无自重叠)配 ids `{"a", "a:b"}`,`("a","b:c")` 与 `("a:b","c")` 照样同拼成 `"a:b:c"`。**两条件都承重,任何一条单独拿出来都是错的。**

### 授权一处行为变更前,要核「触发条件的取值域」,而不只判「该条件下这样改对不对」
- 日期：2026-08-29
- 现象：执行会话报备一处可观测行为变化并请总调度确认边界,描述为「跨类型键碰撞:同键不同 `RecordType` 时从 `Accepted` 改为 Fail-stop `Rejected`」。总调度据此批准,理由是「同键不同类型在证据库里是不可能成立的状态;不可能状态下的返回值不是行为契约,是未定义行为的偶然实现」。**该论证本身成立,却覆盖不到真实击打面**:reviewer 随后发现 `RecordType` 的来源是一个**只受非空约束的自由字符串**,于是**任意两条 ID 相同、该字段不同的普通事件**(与键碰撞毫无关系)也被改成 `Rejected`——那是普通调用,不是不可能状态。同时该改动对自己的目标场景并不健全(同键同类型不同 payload 仍静默去重),故「消灭静默丢记录」是过度声称。执行方主动撤回,总调度作废批准。
- 根因：**授权方按被给的范围推理,却没有核范围本身**。「同键不同 RecordType」听起来是个受控的窄条件,而它窄不窄**取决于该字段的取值域**——那是授权方没问、执行方也没意识到需要说的事实。范围描述是**结论**,结论需要前提,而前提在代码里。
- 规避：①**批准一处行为变更前,先问「这个触发条件的取值域是什么、谁约束它」**,而不是只判断「在该条件下改成这样对不对」;②执行方报备时**主动给出触发条件的来源与约束**(该字段从哪来、受什么校验),不要只给条件的名字;③**「不可能状态」这个论证只在该状态真的不可能时成立**,而「不可能」通常依赖某个未被断言的约束——先找到那个约束,再用这个论证;④**行为变更的健全性与安全性分开判**:堵住一半的洞、同时误伤正常路径,比不堵更差。
- 来源：LumioGameRuntime PR #8 的报备—批准—撤回全过程(2026-08-29);批准与作废均在会话往来中留痕

### 探针本身也会失效——必须先验证变异真的落地、且打中了预期的那一面
- 日期：2026-08-29
- 现象：一天三例「探针跑了、结果看着合理、但它测的不是你以为的那件事」,分布三仓三种失效方式:①LumioClient 的 CI 探针写成 `Assert.True(false, msg)`,被 `xUnit2020` 在**编译期**拦成 build error——它证明的是「构建失败会红」而非「测试失败会红」,不满足该卡验收项;②LumioVoxelEngine QA 的变异探针用 perl 替换,**替换串里的大括号未转义**,变异**根本没施加到文件上**,于是误报 STILL GREEN、几乎把一个健康的测试判成空洞;③LumioCoreEngine 的 DAG 护栏给 `cargo tree` **同时传 `-p` 与 `--workspace`,后者覆盖前者**,护栏因此从未校验真实 DAG,却长期报「11 条违规」——一个全量误报器看起来和一个严格的守护一样凶。
- 补充形态（2026-08-29 追加，第四例，与前三例方向相反）：前三例都是**探针没红 / 变异没落地**;而 LumioClient T-00003 的对照组 A 是**探针红了、颜色对了,红的却是另一件事**——把凭据原始字节拼进出站帧后测试确实变红,但红在 `Assert.NotEmpty() Failure: Collection was empty`:**非 UTF-8 载荷被 Text 帧校验挡在服务端之外,服务端根本没收到,遏制断言压根没机会执行**。交付方由此写下「**探针红了不等于红在该红的地方**」,并顺着这个前提失败发现**原断言只扫原始字节、而 Text 线上的泄漏更可能是拼写形态**,遂补了四种拼写扫描(base64url / base64 / hex / 十进制)。**探针的失败反过来暴露了断言的覆盖缺口,这比探针成功更有价值。**
- 根因：探针是「用来检验守护的守护」,而它自己没有守护。四例的失效点各不相同——被上游工具拦截、变异未落地、参数被覆盖、**红在自证前提上**——共同点是**都会产出一个语法正确、语气笃定的结论**。「测试没红」既可能意味着测试空洞,也可能意味着你根本没改到它;「护栏报红」既可能意味着它在工作,也可能意味着它对一切都报红。
- 规避：①**变异型探针必须先证明变异落地** —— 跑 `git diff` 确认非空,再跑测试;diff 为空时的「全绿」不是证据,是无效实验。**但注意 `git diff` 有一个盲区**:当变异方向恰好是**还原到基线**时 diff 也是空的,而空 diff 在本条纪律里的含义是「没施加」,与事实正相反——此时改用「直接看被改那段代码当前的形态 + 测试转红」双重确认(LumioVoxelEngine 实录);②**「红」和「绿」都要验对方向** —— 红了要看错误消息**是否点名你注入的那处**(而不是别的原因),绿了要确认改动确实还原(`git status` 干净)。**「红」比「绿」更容易让人停止追问**:绿了还会怀疑是不是没测到,红了往往就收工了,所以「红在哪一行」必须和「红没红」一样被检查;③注入的违规**必须是被守护对象真正会遇到的形态**——被编译器/分析器提前拦下的违规,测的是上游工具而不是你的守护;④参数型探针(命令行工具)先单独验证参数组合的实际语义,别假设 `-p` 与 `--workspace` 能叠加;⑤守护若对**已知合法输入**也报红,先怀疑守护本身——全量误报器与严格守护在日志里长得一样,区别只有喂一次正例才看得出来。
- 来源：2026-08-29 三仓实录 —— LumioClient R-00287 交付方自我修正(改用 `Assert.Fail` 重跑并回写重跑实录);LumioVoxelEngine 奇数道 QA 自我更正(重做并校验 diff 非空后确认为 RED);LumioCoreEngine R-00041 的 QA 判定(`cargo tree` 参数覆盖,修复见 `956da90`)

### 守护的判据要做成「输入的纯函数」,反例才能不靠发货路径上的后门来驱动
- 日期：2026-08-29
- 现象：守护类交付反复遇到同一个两难——守护要可测,就得能让它失败;而让它失败的最直接办法是在生产路径上开一个注入点,可那个注入点本身就是守护的绕过口。多张卡因此要么留了测试后门,要么反例只能靠手工临时改文件、跑完还原,无法沉淀成常驻用例。
- 根因：把「采集」与「判据」揉在一个流程里,判据就只能通过真实环境驱动;而真实环境是有状态的,想让它进入失败态就得动生产路径。
- 规避：①**把采集与判据拆开**——采集负责从环境取事实(脚本),判据负责由事实得结论,且**判据是输入的纯函数**;②反例直接**构造输入**喂给判据,于是「清单过期」「登记了不存在的对象」「重复登记」「零发现」「采集输出不可解析」这类失效模式全都能写成常驻测试,**发货路径一个后门都不用留**;③**采集失败与判定失败必须用不同退出码分开**(如 exit 2 vs exit 1),否则环境问题会伪装成代码问题,反过来也一样;④判据的期望值来自**受版本控制的清单**,权威集合来自**独立的第三方来源**(如 `cargo metadata`),发现结果来自**第三个来源**——三方独立才不会自证。
- 来源：LumioCoreEngine R-00266(测试发现失效守护,`origin/main` `edbf4e2`)。该卡先注入 `autotests = false` 证明洞真实存在(30 个测试凭空消失、门禁 exit=0 全绿),再实现;7 项对照组中 5 项即由构造输入直接驱动

### 怀疑一处失败是不是自己引入的,就建对照 worktree 实测,别靠推理
- 日期：2026-08-29
- 现象：改动落地后出现一处构建/测试失败,交付方需要判断它是自己引入的还是既有缺陷。靠读 diff 推理容易两头错——认成自己的会去"修"一个本不该本卡修的东西(夹带),认成既有的又可能放过真的回归。实例:`LumioGameRuntime` 的 `Observability` 在 `netstandard2.1` 目标上编译失败(`System.Threading.Channels` 在该 TFM 不可用),交付方**在未含本 PR 任何改动的 `6a2ab80` 处另开 worktree 构建,报完全相同的两个错误**,从而坐实是既有缺陷(源自 `0754da8`),不属本卡、也不擅自修。
- 根因：「这个失败是谁造成的」是一个**可以直接测量的事实**,却常被当成需要论证的判断。基线 worktree 的构建结果是一次实验,而读 diff 推理是一次猜测——两者的可信度不在一个量级。
- 规避：①判断失败归属时,**在不含本次改动的基线提交上另开 worktree 复跑同一命令**,比对错误是否逐字相同;②相同 → 既有缺陷,**记为 known gap 并说明依据,不夹带修**;不同 → 本次引入,当轮修掉;③这条同样适用于反向场景:交付前若某测试"本来就红",必须先证明它在基线上也红,否则不得以"既有问题"带过;④基线 worktree 用完即删,别让它变成第二个工作区。
- 附:同族失效——**长期不可见的破损**。上例的 `netstandard2.1` 破损在 19/19 全绿期间一直没暴露,因为 `dotnet run --project <测试>` **只构建测试项目的 TFM**;多目标工程的另一个目标从未被构建过。凡「多目标 / 多平台 / 多配置」的工程,**绿灯只覆盖你实际构建过的那一组**。

### 未锚定的忽略模式会在大小写不敏感文件系统上吞掉生成物,而本机显示一切正常
- 日期：2026-08-29
- 现象：`LumioGameRuntime` 的 `.gitignore` 有一行 `artifacts/`,原意是忽略仓库根的 SBOM/依赖报告输出。因未锚定到根,它在大小写不敏感文件系统(macOS 默认)上**同时匹配了 `src/…/Generated/Artifacts/`**——重 pin 新增的 5 个生成文件**被静默忽略,`git status` 里根本不出现**。闸门本身没被骗过(它比对文件系统而非 git 索引),但**本机会误绿,而提交必然残缺**。修法是把 `artifacts/` 改成 `/artifacts/`。
- 根因：忽略模式的匹配面比作者脑中的意图宽,而**忽略造成的失败是"东西不出现",不是"东西报错"**。`git status` 干净在此处不是好消息,是症状。这与「守护空转」不同:那里守护存在但不生效,这里**守护生效、人看到的却是假绿**。
- 规避：①忽略「某个特定目录」时**一律锚定**(`/artifacts/` 而非 `artifacts/`),需要递归匹配才写不锚定的形式,并在同行注释写明意图;②**生成物落地后,用 `git status --ignored` 或 `git check-ignore -v <路径>` 确认它们没被吞**——尤其在新增生成文件、改生成输出目录、或换机器之后;③跨平台仓库把「大小写不敏感文件系统」当默认假设,不要依赖大小写来区分路径;④真正的兜底是**上游侧的完整性闸门在全新 checkout 上跑一遍**——本例正是靠另一会话刚接进 CI 的 generated contract gate 在全新 checkout 上通过,才独立验证了产物完整。
- 来源：`LumioGameRuntime` 重 pin 交付(PR #6,提交 `8ad5981` 一线);独立验证来自同仓 R-00284 接进 CI 的 generated contract gate(main `91ba9a8`)——若那 5 个文件仍被吞,CI 必报 `GENERATED_CONTRACT_DRIFT`

### 派活提示词里写死会腐烂的值,等于给每个执行者发一份过期真值
- 日期：2026-08-29
- 现象：总调度在同一批派活提示词里写死了架构源的 `compilerHash` 具体值,当天该值**变了两次**(`e401077a…` → `870e8635…` → `0aaf61d6…`),**五个跨仓会话拿到的都是过期值**。多个执行会话独立采用了更稳的做法并**主动顶回了这个口径**:用 `git show <rev>:<path>` 做字节级取用、本机重算哈希、证据里记**架构仓提交号**而非哈希;其中一个还先证明「pin 区间内目标文件字节零变化」再决定不动 pin。
- 根因：派活提示词是**一次性快照**,而它引用的上游值有自己的生命周期。把快照当真值分发,等于把「上游何时变」这个不可控变量塞进了每个执行者的正确性前提里。同族错误不限于哈希:任何「行号、计数、文件清单、tip 提交」写进提示词都会腐烂。
- 规避：①派活提示词里**只给不可变锚点**(提交号、tag、符号名),**不给会随上游前进而变的派生值**(哈希、计数、行号);②要求执行方**自己 fetch 后实测读取**,并在证据里记录**它读取时的上游提交号**——这样证据可复核,而不是可疑;③若必须在提示词里给一个值,**显式标注「这是我写这条消息时的实测值,以你自己读到的为准」**;④上游前进后不要无脑跟进 tip,**先 `git diff <pin> <tip> -- <关心的路径>` 证明区间内零变化**,再决定要不要动 pin。
- 来源：2026-08-29 总调度自身失误与五个执行会话的独立更正(LumioNativeCore R-00083、LumioServer R-00271、LumioClient R-00291、LumioCoreEngine R-00020、LumioGameRuntime 重 pin 会话)

### 判据与它的反例测试必须同一提交内诞生,反例的构造方式决定覆盖面
- 日期：2026-08-29
- 现象：一天两次「同一提交内违反自己刚写的规范」,**两例均在 `LumioCoreEngine`**:①其 `.spec/decisions/0007`(随 **R-00016** 交付落地,为 `toml` 依赖选型)明写「只用 toml crate 解析、否决自研子集解析器」,同提交的 `toolchain.rs` 却是手写扫描——把 `supported_hosts` 写成合法多行数组即误报「登记缺失」,错误信息还反向误导;②其 `.spec/decisions/0009`(随 **R-00018** 交付落地)第 1 节写「被背书者与背书者必须不同源」,同提交却让 descriptor 的 `validatorRan` / `entrySymbol` 从被校验对象自己取回去参与重建。两例都由 reviewer 退回时抓出,不是自查发现。(**ADR 编号无机器占号、跨仓存在同号**:本架构仓自己的 `ADR-007` / `ADR-009` 是另两份主题无关的 Accepted 决策,**与这两例无关**,不要读串。)两处都通过了当轮自检——因为新判据落地时**没有一条按该判据构造的失败用例**,判据从写下的那一刻起就是无人守卫的散文。同轮另有一例揭示第二面:同一测试意图,「往文件追加一个字节」的反例必然被抓,「替换某字段的值」的反例却不会,两种构造的盲区完全不同。
- 根因：判据(ADR 条款、「由 X 保证」的声称、门禁规则)是**断言**,而断言不自带执行者。写判据与写守卫判据的测试被当成两件可以分先后的事,先写的那件就永远缺后一件;而即便补了反例,若反例只覆盖「明显改坏」的方向,判据在真实漂移方向上仍然空转。
- 规避：①新增一条 ADR 判据、门禁规则或「由 X 保证」的声称时,**同一提交内必须有一条按该判据构造的失败用例**(先失败、再让实现使其通过),没有反例护航的判据不得合入;②反例要打在**判据真正要挡的那个方向**上,不能只打在「明显改坏会不会被抓」上——落卡/审查时逐条问「这条反例若不存在,判据会在什么情形下静默失效」,把答案写进证据;③一个判据配多种构造的反例(追加/替换/删除/重排/环境注入),覆盖面按构造种类而非用例条数计。
- 来源：`LumioCoreEngine` R-00016 / R-00018 两轮 reviewer 退回实录(两卡均已合入 `origin/main`,分别为 `0b18a1c` / `25808f3`);「反例构造方式决定覆盖面」的附注出自同仓 R-00018 复审——其篡改测试原为「往每份文件追加一个字节」(追加必然改变字节、一定被抓),而「替换某个字段的值」不会,同一测试意图两种构造盲区完全不同。经 TD 总调度自 `docs/plans/2026-08-29-td-handoff.md` §6 升格(提交 `3631110`)。**转述缺口已补齐(2026-08-29)**:仓名与卡号见上,条目现可复核。

### 「由 X 覆盖 / 由 X 保证」的声称,同提交内必须 grep 验证 X 真实存在并留证
- 日期：2026-08-29
- 现象：代码注释、文档与卡面里的「该情形由 X 覆盖 / 由 X 保证」式转嫁声称,其 X 未被机械核实——读者因为有指向而停止追问,而 X 可能并不存在、已改名或从未被引用。**实例**:`LumioCoreEngine` **R-00017** 在三处(`opened_set.rs`、`Cargo.toml`、`tests/test_support.rs`)写「`test-support` 不进运行时闭包由**仓级 `cargo tree` 断言**覆盖」,而 reviewer 一次 grep 就发现**那条断言从未创建**——`just check` 的五个子项(fmt-check / clippy / deny / about / tool-lock)里没有任何依赖图断言,`.github/` 与 `.spec/tools/` 同样零命中。后果可复现:后续任何人给运行时闭包内的 crate 加一条 `features = ["test-support"]` 的 normal 依赖,全套门禁绿灯放行、无一处报警,该不变量的回归保护当时为零。与「守护空转」那条不同的是:那条里守护存在但不生效,这条里守护对象本身可能是空的。
- 根因：转嫁声称把举证责任推给一个**未被机械核实的名字**;写的人当时确实知道 X 在哪,读的人与后来的人只看见名字,而名字不随实现一起腐烂告警。
- 规避：①任何写进代码注释 / 文档 / 卡面的「由 X 覆盖 / 由 X 保证」,**必须在同一提交内 grep 验证 X 真实存在**,并把 grep 命令与输出留进证据评论;②明确 grep 的证明力边界——**它只能证明「X 存在」,证不了「X 的覆盖范围 == 声称的范围」**,后半段仍需对抗审查逐条比对,不得因 grep 通过就整体放行;③X 不存在或范围对不上时,改写声称而不是补一个同名空壳。
- 来源：`LumioCoreEngine` **R-00017** 的 reviewer 退回实录(P1-1,该卡已合入 `origin/main` `071c04e`);处置是把断言真做出来——`cargo tree --workspace -e normal` 白名单断言接进 `just check`(TD 授权在本卡内改 `justfile` 这一共享热点),并按对照组三态给证(注入违规 normal 依赖 → 红并打印违规行 → 移除 → 绿),复审另跑一组反证确认合法用法(dev-dependency 启用该 feature)不误报。同族第二例:`LumioGameRuntime` R-00131 修完行尾层后在同一份 ADR 同一页写下「判据成为 commit 的纯函数」,而全局 `~/.gitattributes` 仍能压过 `-c core.eol=lf`(见「假守护」条规避⑤)。经 TD 总调度自 `docs/plans/2026-08-29-td-handoff.md` §6 升格(提交 `3631110`)。**转述缺口已补齐(2026-08-29)**。

### 生成器 rmtree 输出目录时,「已入库但生成器不产出」的文件每次重生成都被静默删除
- 日期：2026-08-29
- 现象：`tools/lumio_contract.py` 的 `command_generate()` 先 `shutil.rmtree(out_dir)` 再 `copytree` 临时树,而生成器从不产出已入库的 `packages/rust/Cargo.lock`,于是 `generate --out packages` 每次都把它删掉。该误删**已真实合入两次**(`b8f8c50`、`f9c446b`),两次都无人察觉。之所以长期隐形:六个生成 crate 零依赖,事后任何一次 `cargo` 调用都会把锁文件**逐字节**重建,`git status` 随即安静;只有「重生成后不跑 cargo 就提交」的人会带走一次删除,而 CI 的 `cargo check` 在 checkout 之后跑,在 CI 里同样会重建,因此 CI 也看不见。
- 根因：`rmtree` + `copytree` 使输出目录的文件集**等于**生成器 emit 的文件集,但版本库的文件集是**另一个集合**,二者从无机器校验。差集里的文件既没有生成源,也没有守护——它靠「谁都没注意到」存活。同族风险不限于锁文件:凡是「上游工具会重新生成或删除的文件」进了版本库,就把下游门禁绑在了上游的操作纪律上。
- 规避：①**输出目录被整体重建的生成流程,版本库里该目录下的每个文件都必须有生成源**——要么由生成器 emit,要么显式 ignore,不留第三类;②新增此类文件时,守护要**同时**覆盖「缺失」与「内容漂移」两种失效,且**precondition 不能锚在被守护对象自己身上**(用 `packages/rust/Cargo.toml` 是否发布作为前置,若改用 `Cargo.lock` 是否存在,则「文件缺失」这一被守护的失效恰好会让检查静默跳过——守护对自己的失效模式失明);③对照组探针要覆盖**值替换**而非仅追加/删除(追加一个字节必然被抓,替换某个成员的 `version` 值才测得到真正的盲区)。
- 来源：PR [#23](https://github.com/LumioGames/LumioGameEngineArchitecture/pull/23) 顺带发现并刻意留卡(`docs/plans/2026-08-29-td-handoff.md` §3);修法与 `published_cargo_lock_errors()` 见本轮交付

### 「有一份看起来在守护的东西」必须用对照组探针证明它真的会响
- 日期：2026-08-29
- 现象：一天之内四例守护形同虚设,分布四仓、四种机制:①架构仓 `sha256.rs` 的 K[28] 轮常量写错(`0xc6eabbdc` vs FIPS 180-4 的 `0xc6e00bf3`),对任意输入都算错摘要,且当时无 CI 跑 `cargo test`;②GameRuntime `eng/generate-contracts.sh` 的重生成判据**哈希的是经 git attribute 转换后物化的字节,而不是 git 对象本身**——架构源 `.gitattributes` 首行 `* text=auto`,`git archive` 按**调用方**的 `core.autocrlf` 做行尾转换,于是判据是 `(commit, 机器 attribute 栈)` 的函数而非 commit 的函数;③LumioClient 与 ④LumioServer **各自独立**踩中 `Microsoft.CodeAnalysis.BannedApiAnalyzers` 只识别 `BannedSymbols.txt` / `BannedSymbols.*.txt` 的 AdditionalFile,文件名叫 `banned-public-api.txt` 时整份禁令**静默忽略、不报错不警告**——两仓的禁令清单从未生效。四例全部通过过此前的人工审查。
- 根因：守护机制的「存在」与「生效」是两件事,而阅读代码/配置只能确认前者。命名约定型工具(分析器、lint 插件)静默降级尤其危险;记录型守护(manifest/Golden/审计哈希)则会在锚点漂移后腐烂成谎言,同样不报错。
- 规避：①**任何声称有守护的验收项,证据必须是对照组探针**——故意制造一处违规,证明守护会红,再移除证明会绿;只写「build 通过 / 测试通过」不构成守护生效的证据(LumioClient T-00003 的「build 通过即为不使用 Socket 的证据」在闸门空转期间等于零校验);②记录型守护(重生成比对、哈希登记)必须锚定**已提交对象**(`git archive` 只读物化优于 `git worktree add`,后者会向被并发编辑的仓写 worktree 注册记录),并把「产物未被手改」与「与上游同步」拆成两条独立检查——后者只报告不 fail,否则上游每改一次生成器就打断下游;③C# 仓引入 BannedApiAnalyzers 时,AdditionalFile 必须命名为 `BannedSymbols.txt` 或 `BannedSymbols.<描述>.txt`;④**探针要打在「判据本身会不会变」上,不能只打在「改坏了会不会被抓」上**——改 manifest / 填假 commit / 手改 JSON 这类探针全绿,却完全测不到行尾转换那一面;真正抓住它的探针是注入 `core.autocrlf=true` 再跑一遍看结论动不动。跨机比对哈希的地方一律加这类「环境变量注入」探针;⑤**闭合到哪一步就只声称到哪一步**:修完行尾一层后极易立刻写出「判据是 commit 的纯函数」,而全局 `~/.gitattributes` 的 `* eol=crlf` 仍能压过 `-c core.eol=lf`(实测注入敌意 `core.attributesfile` 后干净树报 DRIFT);正确表述是「`(commit, attribute 栈)` 的函数」,并点名未闭合通道(`$GIT_DIR/info/attributes` 无 config 开关、`filter` smudge)。彻底闭合需直接哈希 blob;⑥**探针必须红在被测断言上**——红在前置条件上的探针不算数。实录:把凭据原始字节拼进出站帧,测试确实变红,但红在自证前提 `Assert.NotEmpty`(非 UTF-8 载荷被 Text 帧校验挡在服务端之外,遏制断言根本没机会执行);换成能通过前置的 base64url 拼写后才红在本体(`Assert.DoesNotContain` 命中 `3q2-7xEi`)。**这种探针比空转门禁更危险,因为它「看起来验证过了」**。规避:确认失败消息指向的是被测断言本身,红在前提上就换一种能通过前置的构造再试;顺带反查断言覆盖面(该例暴露出原断言只扫原始字节,而线上泄漏更可能是 base64url / base64 / hex / 十进制拼写)。
- 来源：2026-08-28 K[28] 三方核验与 KAT 补测(架构仓 `bcc8eb9`、`.spec/tasks/sha256-kat-and-three-way-consistency.md`);2026-08-29 SR 会话 R-00131(PR #3 → `6a2ab80`)的两轮 reviewer 证伪与修法;SL 会话 T-00007 与 SA 会话 R-00270/R-00272 的 RS0030 对照组实测
- **更正(2026-08-29,本条初版归因有误)**：初版把 GameRuntime 一例写成「provenance 是假的」。经 reviewer 证伪并由实现方独立复现:五个溯源戳里**四个是同一 commit 在 Windows/`autocrlf=true` 上的忠实渲染,不是伪造**(LF 导出与 `git cat-file blob` 逐字节相等,212 文件 0 不符),唯 `compilerHash` 两种渲染都对不上、确系读了脏工作区。**只修「引用可变来源」那一层,只是把移动靶的轴从「什么时候跑」换成「在哪台机器上跑」**,`4dfc00e`↔`66a71b0` 那次翻烧饼会换个轴无限重演。修法:`git archive -c core.autocrlf=false -c core.eol=lf -c core.attributesfile=<空> ` + pathspec 限定(顺带消掉全树导出的 42 个符号链接在 Windows 上创建失败的问题)。

### SPIKE / 审查结论文档里的 P0 行动项必须当轮落单,否则会躺在文档里过夜
- 日期：2026-08-29
- 现象：LumioClient `docs/spikes/2026-08-28-spike-hybridclr-63.md` §4.7 早在 2026-08-28 就以 probeA/probeB 对照实测记录了「`banned-public-api.txt` 完全没有生效——它是一个 no-op」,§7 风险 B3/R-2 判为「门禁虚假安全感」并写明「必须先修门,再写 loader」,§6 列出 P0-1/P0-2/P0-3 修法与判据。结论正确、证据充分、修法具体——但**没有一条落成任务卡**,于是挂了一夜无人执行,直到次日另一会话独立重复验证后才被处理。同期 LumioServer 又独立踩中同一坑,重复付出发现成本。
- 根因：结论文档的交付定义止于「文档合入」,其行动项没有落单机制;文档评审关注「结论对不对」,不检查「行动项去哪了」。
- 规避：①SPIKE / 审查 / 评估类文档交付时,**P0 级行动项必须在同一轮内落单**,或显式记为「待授权立卡」并写进交回物的 known gaps——两者必居其一,不得只留在正文里;②评审此类文档的卡时,把「P0 行动项是否已落单或显式挂起」列为验收项,不因结论正确就整体放行;③总调度收到含 P0 行动项的文档交付,当轮决定落单归属。
- 来源：LumioClient R-00256(SPIKE-HYBRIDCLR-63)交付与 2026-08-29 SL 会话自我更正;总调度已在 R-00256 补执行状态评论(P0-1/P0-2 已由 T-00007 承接,P0-3 未执行)

### 交回物证据必须引用已推送 origin 的提交,核验第一步是 ls-remote 比对
- 日期：2026-08-28
- 现象：六张「验收中」卡(CoreEngine R-00011..14、Server R-00186/00188)的证据评论引用的提交不在 origin——四张引用 Windows 工作区未推送的本地提交,两张引用的提交虽在 origin 但**不包含所声称的交付文件**(R-00188 声称交付 Cargo workspace,实际引用的是纯文档提交)。同类问题一次核验中发现六处,跨两仓复发。
- 根因：单人多机开发(Windows `C:/Work/LumioGames` 与 macOS `~/LumioGames`),交付会话在本地 main 记证据即流转状态,未推送、未做「提交内容 ⊇ 改动清单」比对;核验方也未曾以 origin 为准复核。
- 规避：①证据评论只准引用**已推送 origin** 的提交号;②总调度核验清单第一步固定为 `git ls-remote` 确认提交在 origin + `git show --stat` 确认提交内容覆盖改动清单;③不满足的卡不得停留在「验收中」以上状态,补差异评论并要求推送后重核。

### 工具链 pin 落卡前先在两台开发机上实测可满足
- 日期：2026-08-28
- 现象：环境性失配一轮对账发现三处:①VoxelEngine 全部测试因 Windows 缺 `link.exe` 从未链接执行(2.4 万行代码只过了 cargo check,审查被迫 RETURN);②GameRuntime `global.json` 锁 SDK `10.0.11` 且 rollForward=disable——该 SDK 版本不存在(是 runtime 版本号),任何机器都无法字面满足,macOS 直接 SDK_MISMATCH 不可构建;③macOS rustup 默认 `x86_64-apple-darwin`(Rosetta),与 aarch64 实机不符。
- 根因：pin 与验收口径按单机现状写死,落卡前未在第二台机器验证过;「验证通过」的声称建立在 type-check 而非链接执行上。
- 规避：①任何 SDK/工具链 pin 写入卡面或仓配置前,须在 Windows 与 macOS 两侧实测该 pin 可解析;②版本 pin 用「SDK 族 + runtime 版本」双口径,不锁不存在的字面值;③`cargo check` 通过不得当作测试证据,验收必须有链接执行的测试输出;④Rust 仓 evidence 记录 host triple。
- 来源：2026-08-28 总调度对账(同上报告 §6.2;R-00112 对账评论、R-00203 审查链)
